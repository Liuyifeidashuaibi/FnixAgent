## 0. 为什么需要这份路线

设计文档完成后，能力清单层面已接近对标（见 §1 评估），但**成熟度不等于功能清单**。当前三项结构性短板：

| 短板 | 表现 | 后果 |
|---|---|---|
| 感知层 O(n) | `snapshot()` 返回 ARIA 树前 80 行 + 最多 60 个带坐标元素 | 复杂页面单次快照数千 token，上下文被撑爆，模型"看花眼" |
| 执行层无等待契约 | 动作后 `wait_for_timeout(600)` 硬编码 | 慢页面必失败、快页面白等，多步操作成功率不可控 |
| 编排层无故障分类 | 只有"驱动降级"，没有"动作级恢复" | 失败只能重试或整体放弃，静默失败（报错成功实则失败）无人拦截 |

**关键判断**：这三项都在 harness 层，与模型强弱无关。BYOK 模式下模型由用户提供，**harness 就是产品本身**——这正是能做出差异的地方。

## 2. 目标架构

```
┌───────────────────────────────────────────────────────────────┐
│ L4 编排层 · 自愈编排器 SelfHealingOrchestrator（新建）          │
│   故障分类 F1-F7 → 恢复动作 → 预算控制 → 结果验证器             │
│   这是"智能"的来源，也是本路线最大增量                          │
└───────────────┬───────────────────────────────────────────────┘
                │ 统一动作契约（ref 寻址，非坐标）
┌───────────────▼───────────────────────────────────────────────┐
│ L3 执行层 · ActionRunner                                        │
│   auto-wait（可见/稳定/可点/未遮挡）· 动作后验证 · 结构化返回     │
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────────┐
│ L2 感知层 · SnapshotRef                                         │
│   确定性 ref（@e1..@eN）· 仅可交互元素 · 紧凑文本 · 带编号截图    │
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────────┐
│ L1 渲染/驱动层 · 三驱动 + 真实渲染                               │
│   Tauri WebView + CDP（内嵌）│ CDP 接管用户 Chrome │ 托管沙箱    │
└───────────────────────────────────────────────────────────────┘
```

**架构核心变化：动作寻址从"坐标"改为"ref"。** 坐标在页面任何变化（横幅出现、字体加载、滚动）后即失效；ref 由快照确定性生成，动作时重新解析，天然抗漂移。

## 3. 分期路线

### Phase 0 · 度量基线（前置，必须先做）

**没有基线就无法证明改进。** 先建三件事：

1. **种子页面集**：5 个固定页面（简单表单 / 中等列表 / 复杂门户 / 重型 SPA / 中文站点），快照存为 fixture
2. **多步任务集**：30 条真实网页任务（搜索→点进→填表→提交、登录态查询、多页采集等），每条带**结果校验函数**
3. **埋点**：每次动作记录 token / 耗时 / 成功 / 失败原因，落到 `driver_events.jsonl` 同源

交付：可一键跑的 `bench_gui_driver.py`，输出上面 5 个指标的当前基线数字。

### Phase 1 · 感知层重构：ref 语义快照 ✅ 已完成（2026-08-29）

替换当前 O(n) 快照为紧凑 ref 模型。

**实测结果**：平均 token 降幅 **77.2%**，峰值 1747 → **389**（目标 ≤400 达成），
最重页面（979 元素）1576 → **304**。

**基线暴露的真问题**（比预想严重）：旧快照把每个元素描述 2-3 遍（ARIA 树里
`text:`/`textbox` 重复 + 坐标列表再列一遍），15 元素的表单就要 496 tokens；
重型页面因 `lines[:80]` + 60 元素上限**静默截断**到只可见 6%——既贵又不完整。

- `SnapshotRef` 数据结构：`{ref, role, name, 状态(可点/禁用/可见), 位置}` 仅收**可交互元素**
- 快照格式：紧凑文本行，目标单页 200-400 token
- **带编号截图通道**（对标 Agent Browser `--annotate`）：需要视觉判断时，截图上叠加 ref 编号，模型可直接说"点 @e7"
- 保留完整 ARIA 树作为**按需深挖**通道（默认不返回）
- 寻址解析：ref → 内部稳定 selector（优先 `data-*`、aria、role+name 组合，最后回退结构路径）

依据：Agent Browser 实测重型页 200-400 tok vs Playwright MCP 10,162 tok。

### Phase 2 · 执行层：auto-wait + 动作后验证 ✅ 已完成（2026-08-29）

- 每个动作内置 auto-wait：元素存在 → 可见 → 位置稳定（连续 2 帧位移为 0）→ 未被遮挡 → 可接收事件
- **删除全部 `wait_for_timeout` 硬编码**，改为状态等待；确需等待必须走显式原语
- 显式等待原语：`wait_for(text | ref | url | network_idle | download)`（Phase 2 落了 text/selector 两路）
- 动作后结构化返回：`{ok, changed, url_changed, new_refs, dom_diff_summary, error_class}`
- `changed` 是关键：点完页面没反应 = 失败，即使没抛异常

**实测结果**（`bench_gui_driver.py` A/B，旧实现用固定 sleep(600ms) 复现）：

| | 固定 sleep(600ms) | 状态等待 | 结论 |
|---|---|---|---|
| 瞬时动作耗时 | 672.9ms | **413.5ms** | **快 38.5%**（目标 30% 达成） |
| 延迟 700ms 生效的动作 | **捕获=False** | **捕获=True** | 旧实现**静默失败** |
| 点了没反应 | — | changed=False ✅ | 静默失败可拦截 |

**这条 A/B 的价值不止是"快了 38%"**——它实证了旧实现会产出静默失败：延迟
渲染的点击被判定为"点了没反应"，模型要么放弃要么重复点击。这不是理论推演，
是 A/B 跑出来的。

**实现要点（三重等待信号，缺一不可）**：

1. **DOM 静默**——连续 `quiet_ms` 无 MutationObserver 事件
2. **定时器排空**——动作回调里 `setTimeout(fn, 700)` 的延迟渲染，在 DOM 上表现为
   "先静默再变"，只看 DOM 会在静默期误判完成
3. **网络空闲**——fetch/XHR 在途时 DOM 必然还会变

只统计动作**之后新发起**的定时器与请求，且受波次上限（12）保护——带心跳或
动画循环的页面不会被拖到超时上限。两条护栏测试锁住这个性质：瞬时动作不得
接近超时上限、动画页面不得被自续循环钉死。

### Phase 3 · 编排层：自愈编排器（核心）✅ 主体已完成（2026-08-29）

直接实现 arXiv 2606.01416 的结论。

**交付**：`core/tools/orchestrator.py`（策略核心，与驱动无关）+ `core/tools/browser_healing.py`（浏览器接线）。

**实测结果**（真 Chromium 端到端，`test_browser_healing_e2e.py` 6 项 + `test_orchestrator.py` 15 项全绿）：

| 场景 | 不经自愈 | 经自愈 |
|---|---|---|
| 点中同名诱饵按钮（点了没反应） | **当作成功**，模型误以为提交完成 | 判 F4 → 换同名候选 → 命中真按钮 |
| DOM 重渲染导致 ref 失效 | 直接失败 | 判 F5 → 重新快照 → 按**元素名**映射到新 ref → 成功 |
| 确实无解 | 重试到放弃 | 2 次内收敛并上报，不空耗预算 |

**三个实现要点，都是实测逼出来的，不是照论文抄的**：

1. **substitute 换的是"同名候选"而不是"换寻址方式"**。最初按 ref ⇄ 文本互切
   实现，实测发现 Playwright 的 `get_by_text(...).first` 每次都命中同一个
   诱饵——等于没换。页面上排前面的同名按钮常常正是干扰项，逐个试过去才有效。

2. **帮不上忙的那一级要标记成死路**。钩子返回 None 表示该恢复路径无从下手，
   此时应跳到阶梯下一级。否则 F5 的三级阶梯里 `refresh` 会先耗光自己的 2 次
   预算，把后面的 `substitute`/`replan` 饿死。

3. **文本寻址先解析成 ref 再点击**。这样"换目标"才有可枚举的候选集；直接
   `click_text` 没有候选概念，无法做替换。

**验证器（verifier）**：动作没抛异常、甚至 `changed=True`，但只要结果不满足
预期仍判失败并归 F6 走重规划。这是静默失败的最后一道闸——论文中非验证方法
13.2–17.6% 的"看似合理但错误"正是漏在这里。

**预算是任务级的**：`reset()` 前跨步骤累计。每步重置会让"失败的恢复尝试也
消耗预算"这条约束形同虚设。

### Phase 0 补完 · 任务级基线 ✅ 已完成（2026-08-29）

交付：`benchmarks/gui_driver/minisite.py`（自建电商站点）+ `tasks.py`（35 条任务）
+ `run_tasks.py`（跑分与静默失败度量）。

**实测**：正例成功率 **100%**（32/32）、静默失败率 **0%**、负例正确拒绝 **100%**
（3/3）、谎报成功 **0 条**、自愈触发 78 次、平均任务 2.5s。

**执行策略说明**：用**固定策略（scripted policy）**代替模型消费快照。BYOK 模式
下模型由用户提供，harness 的度量必须把模型变量固定住——否则测出来的是模型
能力，不是 harness 能力。策略只能读快照 + 按名称匹配，与模型所见信息等价。

**为什么必须配负例**：只测正例的话，"永远报成功"的驱动能拿满分。所以加了
3 条不可能完成的任务（点不存在的商品、未登录点不存在的按钮、无结果时硬点），
判据是**它必须承认失败**。谎报成功比失败危险得多——那正是 Agent 对用户撒谎
的形态。

**这个 100% 的含金量要如实看待**：站点是自造的，任务是自己出的，策略是固定
的。它证明的是"这条链路上没有系统性缺陷、静默失败为 0、不可能的任务会被
拒绝"，**不能证明真实网站上的表现**。真实站点的分布更脏（弹窗、懒加载、无限
滚动、iframe、验证码），需要后续补真实站点任务集。

**本轮基线逼出的两个真缺陷**（都不是推演，是跑出来的）：

1. **导航后新文档没装探针** → 跳转之后的等待形同虚设，延迟渲染必漏。
   修复：探针改用 `add_init_script` 注入（每个新文档、且在页面脚本之前），
   并在检测到文档被替换时重新挂 MutationObserver。旧实现在 evaluate 抛
   "Execution context was destroyed" 时直接 return，等于"跳转后完全不等"。
   修复前 60% → 修复后 73.3%。
2. **动作效果不可见时无法判定成败**（只写 localStorage 的加购）。这是原理性
   限制而非实现缺陷：DOM 观察不到就无从判断。当前策略是**保守判失败**并触发
   换目标——宁可多试，不可假装成功。

**七类故障 → 八种恢复动作**

| 类 | 故障 | 恢复动作 |
|---|---|---|
| F1 | 工具超时 | 指数退避重试（带抖动） |
| F2 | 参数/模式错误 | 参数修复（本地修正，不消耗模型） |
| F3 | 输出格式错误 | 带 schema 重问 |
| F4 | 工具选择错误 | 工具替换（如 click_text → click ref） |
| F5 | 上下文过期 | 上下文刷新（重新快照后再决策） |
| F6 | 证据矛盾 | 重规划 |
| F7 | 控制循环（原地打转） | 终止 + 上报用户 |

**预算机制**：retry / replan / substitute / escalate 各自独立上限，失败的恢复尝试同样消耗预算。（`Budget`，已实现）

**结果验证器（verifier）**：任务结束前用校验函数判定真实结果，杜绝静默失败。论文中非验证方法 13.2–17.6% 返回"看似合理但错误"的结果，验证器把它降到 0。（已实现，`execute(verifier=...)`）

**可观测**：每步记录 `{step, action, failure_class, recovery_action, budget_left, verified}`，与既有审计流合并。（已实现，`StepRecord.to_dict()`）

当前截图流 → 真实渲染。

**方案**：Tauri v2 独立 browser WebView，仅对该窗口开 `--remote-debugging-port`，后端 Playwright `connect_over_cdp` 控制同一页面。

依据（2026-08-29 调研实证）：
- `Haprog/tauri-cdp` 已验证：Tauri 2 + Edge WebView2，设 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`，Playwright `chromium.connectOverCDP('http://localhost:9222')` 可直连
- 两种开启方式：环境变量（进程级）或 `tauri.conf.json` 的 `additionalBrowserArgs`（窗口级，**推荐**，可只对 browser 窗口开）
- Playwright 官方也有 WebView2 文档页

**硬约束与风险**：
- 仅 Windows/WebView2 可用；macOS(WebKit2GTK) 与 Linux 需另行方案 → 跨平台时保留截图流作为降级
- **安全**：CDP 无鉴权，任意本地进程可驱动。必须对 browser 窗口开、**主窗口绝不开**、绑 127.0.0.1、用非标准端口、release 构建需评估
- WebView2 单窗口单页面：多 tab（原 N3）需用多窗口或单 WebView 复用 + 应用层 tab 条，架构需重新设计

**降级**：真实渲染不可用时自动回退截图流，前端无感。

**本轮交付**：

- `apps/workbench/src-tauri/src/browser_window.rs`（新）：开独立 browser 窗口，
  仅对它加 `--remote-debugging-port=<动态端口> --remote-debugging-address=127.0.0.1`；
  Windows 上配独立 `data_directory`（Tauri 硬要求，否则建窗失败）
- `driver_router.probe_cdp()`：**内置窗口端口优先于**接管用户浏览器端口
- `POST/GET /api/v1/browser/real-render`：前端登记端口 / 查询状态
- `apps/workbench/src/shell/desktop/realRender.ts`（新）：开窗口 + 登记端口，
  失败静默降级；`BrowserView.tsx` 加"真实渲染"模式标记与面板

**安全处理（这一段比功能本身重要）**：CDP 没有任何鉴权，任何本机进程都能
完整操控开了它的浏览器。因此只对 browser 窗口开、主窗口绝不开、绑 127.0.0.1、
**端口动态分配**（固定 9222 等于给攻击者一个稳定靶子）。

**⚠️ 未验证的部分——必须说清楚**：

- 三方代码均通过编译/类型检查（cargo check ✅、tsc --noEmit ✅、86 项 Python
  测试 ✅），但**没有真机跑过**：没启动桌面端验证 WebView2 是否真的开了端口、
  Playwright 能否 attach、attach 后是否与主窗口正确隔离
- 单测只覆盖了 Python 侧契约（端口优先级、回退、清零），Rust 与 TS 侧**无测试**
- 因此本项**不计入已完成**，需一次真机冒烟：启动桌面端 → 地址栏输入网址 →
  确认弹出独立窗口且 `driver_mode` 变为 `cdp-attach` → 确认文本可选中

**平台限制**：仅 Windows/WebView2。macOS(WKWebView) 与 Linux(WebKit2GTK) 无
`additionalBrowserArgs`，Rust 侧直接返回 unsupported，前端回退截图流——不做
半吊子实现。

### Phase 5 · 工具表面收敛 + 录制回放 ✅ 已完成（2026-08-29）

- **收敛工具集** ✅：8 个 `browser_*` → 2 个正交原语 `browser_view`（读）/ `browser_act`（写），按**读写分离**切，权限边界天然清晰。旧 8 个实现保留但默认不注册，`FNIX_BROWSER_LEGACY_TOOLS=1` 可重新暴露做 A/B 与回滚——收敛是结论，但保留被证伪的余地
- **录制回放** ✅：用户演示 → 录制轨迹（ref + 元素名 + 参数 + 每步状态断言）→ 重放。高频重复操作（登录、填固定表单）直接质变
- 轨迹落盘 v1 JSON，字段与审计流（StepRecord）对齐，一份数据两用

**录制/重放的三个设计要点**（都是前几期踩过的坑里长出来的）：

1. **按元素名解析 ref，不按编号**。ref 编号按 DOM 遍历顺序生成，页面多渲染一个元素编号就整体后移。照编号重放等于把录制瞬间的 DOM 结构当永久契约，正是 F5（上下文过期）的来源。名字匹配不到时才退回编号，并在日志里说明。
2. **每步带状态断言，不符就停**。录的时候记下动作**之后**的 URL 与"页面是否真变了"。只有一种情况定为致命：**录制时变了、重放时没变**——那就是"点了没反应"，静默失败最典型的形态。反方向只记警告（可能只是多了个动画）。没有这条断言，重放就会"静静成功"。
3. **输入字面值默认不落盘**。type 动作录的正是用户敲进去的东西，演示一次登录那就是密码。默认只记"这一步需要输入"，重放时当次传入（可按步骤序号或元素名）。确需连内容一起录（如搜索关键词）显式开 `capture_values=True`。

**为什么走 API 而不是再加两个工具**：Phase 5 刚把模型可见工具从 8 个收到 2 个，依据就是"每多一个工具，模型就多一次选错的机会"。录制是用户在面板演示，重放是编排层调用，两者都不需要模型在工具列表里做选择——所以暴露成接口，收敛成果不被破坏。

**实测证据**（真 Chromium + 自建站点，非 mock）：

| 用例 | 验证点 | 结果 |
|---|---|---|
| 录制登录 → 重放 | 重放后**真的处于登录态**（不只断言"没报错"） | ✅ 4 步全通过，`localStorage.user` 已写入 |
| 重放漂到同名诱饵 | 状态断言拦下"点了没反应"，不静默成功 | ✅ 停在 step 0，购物车为空 |
| 接自愈层重放 | 换目标后购物车**真的多出一件 p01** | ✅ 恢复成功 |

**接口**：`POST /browser/trajectory/record/{start,{rid}/step,{rid}/stop}`、`GET|DELETE /browser/trajectory/{tid}`、`POST /browser/trajectory/replay`。轨迹存 `~/.fnix/trajectories/`，id 走字符白名单（防路径穿越）。

**过程中修掉的一个真 bug**：轨迹 id 最初只对名字做字符清洗，"登录演示" 与 "搜索流程" 都会被清成 `____` 而互相覆盖。现统一在名字后带录制会话号，ASCII 名保持可读、中文名退化成 `traj-<rid>`，两种情况都不撞车（有回归用例）。

### Phase 6 · 泛化能力：脏页面压力集 ✅ 已完成（2026-08-29）

Phase 0 那 100% 是在**自建干净页面**上拿到的，它证明的是"链路上没有系统性
缺陷"，回答不了"上了真实网站会不会崩"。这一期就是来回答后者的。

**为什么不直接拿真实网站跑**：三个硬伤，想清楚之后放弃。

1. **不可复现**——网站改版、A/B 分桶、反爬，同一条任务今天过明天挂。基线一漂，
   就分不清"产品变好了"和"网站变了"，度量意义归零。
2. **不可判定**——真实站点上很难稳定断言"是否真加进了购物车"，最后往往退化成
   "动作没报错就算成功"，而这正是静默失败的定义。
3. **失败归因困难**——真实页面上十几个恶劣特征叠加，失败了说不清是哪一个。

**替代方案**：把真实网站的恶劣特征提取成**一次只脏一个地方**的可控 fixture。
可复现、可判定、可归因，于是能进 CI——这是真实网站永远做不到的。

`benchmarks/gui_driver/dirtysite.py`（12 个页面）+ `dirty_tasks.py`（15 条任务）
+ `run_dirty.py`（跑分），口径与 Phase 0 完全一致：成功率 / 静默失败率 / 谎报数。

**第五轮（2026-08-30）：把"像真人用浏览器"补齐成产品**——多标签页（N3：

N1 接管引导（调试端口一键指引，全部独立配置目录 + 首次选择记忆）。桌面驱动

**负例比正例更要紧**：只测正例的话，"什么都点得到、什么都报成功"的驱动能拿
满分。5 条负例守的是"做不到时如实说"——其中 `n05`（目标在 iframe 里）尤其
关键，外层摆着一个同名倾向的按钮，硬凑的话很容易"成功"，而购物车里什么都没有。

**这一期抓出来的四个真 bug**（都是压力集逼出来的，不是设计时的构想）：

1. **近似名截胡（最危险）**。名称匹配原本是双向包含，于是 AI 说"加入购物车"
   会被 DOM 里排在前面的"加入购物车并结算"命中。点了、页面变了、没报任何错
   ——从 harness 视角是一次干净漂亮的成功，而用户看到的是"我说加购，它直接
   下单了"。改为**分档匹配**：完全相等 > 元素名包含查询 > 查询包含元素名，
   同档取名字更短的。生产路径（`browser_healing`）与兜底路径
   （`click_text` 的 `get_by_text(exact=False)`）一并修掉。
2. **`<summary>` 被标成 generic**。折叠面板的展开控件在快照里没有任何特征，
   内容藏在面板里时模型不知道该先点哪个。现在报 `role=summary`。
3. **感知层盲区检测是死代码**。`_COLLECT_JS` 算了 canvas 盲区，但
   `collect_refs` 没往外传，`RefSnapshot.canvas` 永远是空 dict——
   `has_canvas_blind_spot` 恒为 False。画布页拿到空快照却什么提示都没有，
   模型只会读作"页面是空的"然后开始编造。现改为结构化返回 `CollectedRefs`，
   并在**快照非空时也要提示**（画布页常配着几个真按钮，空快照分支根本不触发）。
4. **单测污染用户配置**。域名策略测试会写真实的
   `~/.local/share/fnixagent/browser_policy.json`，批准过的域名被永久记住，
   于是同一套测试第二次运行时目标域名已是"此前已批准"、确认闸不再触发
   ——首次全绿，再跑就红，用户配置里还多出一条 `gate.example.com`。

**已知盲区（不掩饰）**：~~同源 iframe 内的元素目前不在 ref 寻址范围内~~
——2026-08-30 第六轮已落地跨 frame 寻址：帧树 BFS 收集 + `frame_locator` 链
透明解析，同源/跨域帧均可按 @ref 操作；深度上限 3 层之外仍如实报盲区。
canvas/WebGL 内容无法读懂，只能如实提示并引导走截图通道。

## 4. 关键技术决策与依据

| 决策 | 选择 | 依据 |
|---|---|---|
| 元素寻址 | ref（确定性标识）而非坐标/选择器 | 坐标随页面变化失效；选择器随前端重构失效；ref 由快照生成为准 |
| 快照内容 | 仅可交互元素 | 重型页 token 差 25-50x（Agent Browser 基准） |
| 等待策略 | 状态等待 + auto-wait | 硬编码 sleep 在慢页面必失败；Playwright MCP 的 auto-wait 是其稳定性核心 |
| 探针注入 | `add_init_script` 而非动作前 evaluate | 后者只对当前文档有效，跳转一次即失效——实测 30 条任务里 5 条栽在这 |
| 失败恢复 | 先分类再恢复 | 静态 70.1% → 重试 94.5% → 分类恢复 98.8%（arXiv 2606.01416） |
| 结果校验 | 必须验证器 + 配负例 | 静默失败 13.2-17.6% → 0%；只测正例无法识别"永远报成功"的驱动 |
| 渲染 | Tauri WebView + CDP | 已实证可行；截图流无法选中文本/原生输入 |
| 工具数量 | 收敛而非堆砌 | 17→2 后成功率 80%→100%（Vercel 内部） |
| 工具切分 | 按读写分离（view/act）而非按动作 | 切分必须正交、无重叠，否则模型仍要"选哪个"；读写天然正交且权限边界清晰 |
| 重放定位 | 按元素名而非 ref 编号 | ref 编号随 DOM 遍历顺序漂移；实测中文站点与动态列表都会触发 |
| 重放校验 | 每步状态断言，不符即停 | 只看"没报错"会让重放静静成功——实测重放漂到同名诱饵时驱动层零报错 |
| 轨迹落盘 | 输入值默认不落盘 | 演示一次登录，type 录的就是密码；敏感值改为重放时当次传入 |
| 录制/重放暴露面 | API 而非新增工具 | 录制由用户演示、重放由编排层调用，都不需要模型做工具选择；否则破坏收敛 |
