# 界面驱动 · 核心任务、现况与下一步方案

> 制定：2026-08-29　|　前置：`GUI_DRIVER_ROADMAP.md`（分期路线）
> 本文件回答三个问题：**核心任务是什么**、**现在真实处在什么位置**、**接下来按什么顺序做**。
> 纪律沿用路线图：指标没测出来就算没完成，不许用"应该可以了"结项。

---

## 1. 核心任务

BYOK 模式下模型由用户提供，**harness 就是产品本身**。核心任务一句话：

> 让「AI 通过工具操作真实界面」这件事**可信**——成功是真成功，失败会被如实
> 报告，而且换到脏页面上依然成立。

拆成三条可度量的承诺，每条都有对应的反指标：

| 承诺 | 度量 | 反指标（必须压到 0） |
|---|---|---|
| 不说谎 | 任务成功率（verifier 判定真实结果） | **静默失败率**、**谎报成功数** |
| 不脆弱 | 快照 token、动作耗时、自愈覆盖 | 硬编码 sleep、"点了没反应"当成功 |
| 可泛化 | 脏页面压力集通过率 | 只在自己造的干净页面上漂亮 |

三条里**"不说谎"优先于其余一切**。一个 60% 成功率但每次失败都如实上报的
harness 是可用的——用户会自己接手；一个 95% 成功率但 10% 静默失败的 harness
不可用，因为用户分不清哪 10% 要复查，最终只能全量复查，等于没有自动化。

这就是为什么要配负例：只测正例的话，"永远报成功"的驱动能拿满分。

### 2.2 本轮实测出的四个真问题（都不是推演，是跑出来的）

**问题一：真实渲染模式下，AI 驱动的根本不是用户看到的那个页面。**

`_ensure_cdp_attach` 对两种 CDP 端点一视同仁地 `new_page()`。对内建真实渲染
窗口这是原理性错误——真实渲染的全部意义就是"AI 与用户面对同一个页面"，
`new_page()` 开出来的是一个用户看不见的 tab。

后果比截图流更糟：截图流至少诚实，用户知道自己看的是图片；而这里用户以为
在和 AI 一起看同一个页面，实际上 AI 在另一个页面里点，**连"看错了能发现"
这个最后的人工兜底都没了**。

同一根因还带了第二个 bug：`close()` 与 `_demote_to_managed()` 无条件关闭
`self._page`，会把真实渲染窗口的页面关掉（用户看到白屏）。

**问题二：感知层有两个静默盲区。**

- Shadow DOM 内的元素不在 `document` 树里，`querySelectorAll` 扫不到 →
  模型看不见，也就永远不会去点，且不报错、不失败。表现为"页面上明明有个
  按钮，AI 说没有"。
- 被固定层盖住的元素没有任何标记 → 点击被上层接走，驱动层可能一句错都不报。

**问题三（最关键）：自愈把"够不着"当成了"选错了"。**

故障分类把 `intercepts pointer events` / `not visible` / `not stable` 与
"目标选错"一起归为 F4，恢复动作一律是 **substitute 换同名候选**。脏页面
基线 d05 实测后果：

```
指令：加购 A → A 的按钮被固定顶栏压住点不动 → 判 F4 → 换同名候选
→ 点到 B 的「加入购物车」 → 驱动层零报错 → 任务判"成功"
→ verifier 发现购物车里是 B，不是 A         ← 静默失败
```

**够不着 ≠ 选错了。** 换目标在这里等于替用户改意图，而且改完不报错——把一次
诚实的失败换成一次无人发现的做错。

**问题四：没有能证明泛化能力的度量。**

Phase 0 的 100% 建立在**自造的干净页面**上：元素稳定、位置固定、点了就有
反应。它证明的是"链路上没有系统性缺陷"，证明不了"上真实网站会不会崩"。

**问题六（第二轮扩大对抗面后实测新增）：近似名截胡——最危险的一类静默失败。**

名称匹配原本是双向包含（`q in n or n in q`），于是 AI 说"加入购物车"会被
DOM 里排在前面的"**加入购物车并结算**"命中。这一类的恶劣之处在于**完全
没有异常**：按钮点了、toast 弹了、页面状态变了，从 harness 视角是一次干净
漂亮的成功。真实电商/支付页面上"加入购物车"与"加入购物车并结算"就是并排
摆着的，用户说加购，AI 直接给下单了。

跑分策略与生产自愈层共用同一套匹配，所以它不是"基准的 bug"，是产品的 bug。

**问题七：`<summary>` 在快照里被标成 `generic`。**

折叠面板的展开控件在模型拿到的上下文里没有任何特征——内容藏在面板里时，
模型看到的是一坨没有名字的元素，不知道该先点哪个才能把内容放出来。

**问题八：感知层的 canvas 盲区检测是死代码。**

`_COLLECT_JS` 算出了 canvas 盲区，`collect_refs` 却没往外传，
`RefSnapshot.canvas` 永远是空 dict，`has_canvas_blind_spot` 恒为 False。
画布页拿到空快照却一条提示都没有，模型只会读作"页面是空的"，然后开始编造
——这比报错糟糕得多。

**问题九：单测污染用户真实配置，而且会自毁。**

域名策略测试会写用户的 `~/.local/share/fnixagent/browser_policy.json`，
批准过的域名被永久记住。于是同一套测试第二次运行时目标域名已是"此前已批准"、
确认闸不再触发：**首次全绿，再跑就红**，用户配置里还多出一条
`gate.example.com`（2026-08-29 实测复现）。

单测改写用户配置本身就是缺陷，测试自毁只是它最容易被看见的那一面。

### 2.3 接线审计：文档声称的 vs 代码实际接上的（2026-08-29）

按"删掉它，用户能感知吗"逐条过了一遍。三档结论：

**真接线（删掉用户立刻能感知）**

| 机制 | 判据 |
|---|---|
| changed 静默失败闸门 | `_act` 算签名差 → `_outcome_from(require_change)` → 生产两个入口（`browser_act` 工具、API `/browser/action`）全走 healer；遗留 8 工具默认关闭 |
| auto-wait + 状态等待 | 无"点完 sleep 等生效"残留；仅存的 `wait_for_timeout` 是状态轮询粒度，重试退避是退避不是等待 |
| obscured → clear_obstruction 闭环 | 感知层标 → `click_ref`/`type_ref` 动作前自动消费 → F8 阶梯也接了。删掉 dirty d05 会从通过变失败（实测过） |
| 分档名称匹配 | 删掉 dirty d07 会点到"加入购物车并结算"（实测过） |
| F1/F4/F5/F8 恢复钩子 | retry（内联）/ substitute / refresh / clear_obstruction 均已注册 |

**部分接线**

- **域名信任策略**：判定逻辑接在 `navigate` 上，但**此前没有任何配置接口**——
  只能手工改 `~/.local/share/fnixagent/browser_policy.json`。文档写"用户可配置
  的受信任域列表"，实际是"用户得会找隐藏文件并手写 JSON"。
  **本轮补了 `GET/PUT /browser/domain-policy` + approve/revoke/check 四个接口。**
- ~~F6 证据矛盾~~（第三轮已修复）：原阶梯第一级 REPLAN 未接线（重规划需要
  模型，驱动层不代劳是刻意的），落到 REFRESH。后来发现 REFRESH 在这里不是
  烧预算那么简单——**它会把「结果不对」伪装成「点了没反应」**：验证器说结果
  不对时动作本身已成功，刷新上下文会重执行同一个动作，第二次执行页面当然
  不再变化，F6 被改判成 F4。记者从「没反应」查起，永远查不到真相。
  修法：F6 阶梯 = `(REPLAN, ESCALATE)`，刻意不含 REFRESH（`orchestrator.py`
  阶梯表内有详细注释），配正向+反向两条回归用例锁定。

**名义完成（删掉用户无感知，或只在空气里烧预算）**

- **F2 参数错**：会真实触发（`classify` 把非元素类的 `ValueError` 判为 F2），
  但阶梯 `(FIX_ARGS, REPLAN, ESCALATE)` 三级钩子**一个都没注册**。修之前每级
  先扣一格预算再发现无事可做——**预算是任务级的，被空气烧掉之后，同一任务里
  真正能救的 F5/F8 就没预算了**。
  修法：未接线的动作在挑选阶段直接跳过，不占预算；并新增
  `orchestrator.unwired_recoveries` 属性，让"名义完成"在代码里就可见，
  不必等人工审计。
- **F3 输出格式错**：`classify` 的关键词规则里**没有任何一条指向 F3**，
  浏览器路径完全不可达。分类、阶梯、RECOVERY_HINT 三样俱全但永远不触发。
  已在 `driver_errors.py` 注明，不算进"F1-F8 都有定向恢复"。
- **回归保护**：见下一条。

**问题五（最严重）：CI 零覆盖。**

```
git ls-files src/fnixagent/core/tools/browser.py        → 空
git ls-files tests/unit/test_browser_refs.py            → 空
```

八个实现文件（`browser*.py` / `driver_*.py` / `orchestrator.py` /
`browser_policy.py`）连同全部 browser/orchestrator 测试、基准、文档，
**一个都没入库**。而 CI 跑的是全量 `pytest tests/unit/`
（`.github/workflows/ci.yml:101`，不是白名单）——文件不在仓库里，
CI checkout 后压根不存在，**静默跳过而非失败**。

结论（2026-08-29）：**本地 167 项全绿，CI 一项都没跑。** 前几轮宣称的
Phase 1/2/3/5/6，在版本控制层面完全不存在：无法 review、无法回滚、
无回归保护。

**已解决（2026-08-30）**：全部实现 / 测试 / 基准 / 文档按四批分层提交

```

→ did not match any file(s) known to git
```

`browser.py`、`browser_refs.py`、`browser_healing.py`、`browser_trajectory.py`、

## 3. 本轮改动

### 3.1 Phase 4 · attach 归属（`browser.py`、`driver_router.py`）

区分两种 CDP 归属，语义相反，不可混用：

| 归属 | 场景 | 语义 | 结束时 |
|---|---|---|---|
| `builtin` | 内建真实渲染窗口 | **接管用户可见的那个页面** | 只断开连接，绝不关页面 |
| `user` | 接管用户日常浏览器 | 新开自己的隔离 tab | 只关自己的 tab |

- `probe_cdp_target()` 连同归属一起返回（`probe_cdp()` 保留，只返回地址）
- builtin 分支会等可见页面挂上来（Tauri 建窗与 WebView2 首屏是异步的，
  connect 成功那一刻 `pages()` 可能还是空的）
- 真实渲染窗口的页面**永不归会话关闭**，包括兜底新建的——关掉它等于关用户
  的窗口，这比泄漏一个 page 严重得多

### 3.2 感知层 · 补两个盲区（`browser_refs.py`）

- **穿透 open shadow root**：递归收集。解析侧不用改——Playwright 的 CSS 引擎
  本来就穿透，`[data-fnix-ref=eN]` 照样定位得到。
- **标记 `obscured`**：用 `elementFromPoint` 判断元素中心点真正接到事件的是
  不是它自己（跨 shadowRoot 的宿主链一并比较）。
- **报告 iframe 盲区**：不枚举 frame 内元素，但把"那里有 N 个可交互元素"
  写进快照文本。**静默的感知盲区比显式的能力缺口危险**——前者让模型以为
  世界上没有那个按钮，后者至少还能让人去补。

### 3.3 感知 → 执行闭环（`browser.py`）

感知层标记了 `obscured`，执行层就得用上这个信号，否则标记只是装饰：

- `clear_obstruction(ref)`：把目标滚动到视口居中。**只滚动，不用 JS 触发
  click**——那会绕过真实用户能收到的所有事件，让 AI 走一条用户永远走不通的
  路，等于把静默失败换成另一种静默失败。
- `click_ref` / `type_ref` 在动作前自动消费该信号。

### 3.4 F8 目标不可达（`driver_errors.py`、`orchestrator.py`、`browser_healing.py`）

- 新增 **F8 目标不可达**，从 F4 里拆出来（"够不着" vs "选错了"）
- 新增恢复动作 **CLEAR_OBSTRUCTION**（解除遮挡后重试**同一个**目标）
- F8 阶梯 = `(clear_obstruction, refresh, escalate)`，**刻意不含 substitute**
- `substitute` 钩子遇到 F8 主动返回 None（死路），即便被别的阶梯调到也拒绝换目标

### 3.5 脏页面压力集（`benchmarks/gui_driver/`）

`dirtysite.py` 生成 6 类对抗性页面，`dirty_tasks.py` 配意图级任务与结果
校验器，`run_dirty.py` 跑分。每个页面只隔离**一种**恶劣性质，失败可直接归因。

| 页面 | 隔离的性质 |
|---|---|
| consent | 全屏遮罩挡住主内容 |
| lazy | 内容滚动进视口才渲染 |
| infinite | 滚动到底才追加 |
| rerender | 列表每 400ms 整体重建并随机排序 |
| sticky | 固定层盖住目标（锚点跳转后） |
| shadow | 目标在 Shadow DOM 内 |

**为什么不用真实网站做基线**：不可复现（改版/A-B/反爬让基线漂，就无法区分
"产品变好了"和"网站变了"）、不可判定（真实站点上很难稳定断言"是否真的加进
购物车"，最后退化成"没报错就算成功"，而那正是静默失败的定义）、失败归因
困难。把恶劣特征提取成可控 fixture 之后，可复现、可判定、可归因，因而能进 CI。

### 3.6 第二轮：扩大对抗面 + 修掉它逼出来的四个 bug

第一轮 6 个页面太少，且每条只脏一处，于是扩到 **12 页 / 15 条任务 / 11 种
性质**。新增的都是真实站点上高频且此前完全没覆盖的：

| 页面 | 新增的性质 |
|---|---|
| decoy | 近似名诱饵，且**故意排在目标前面** |
| accordion | 目标藏在折叠面板里 |
| slow | 首屏空，1.5s 后才有内容（测过早放弃） |
| virtual | 虚拟列表，DOM 节点复用、ref 随滚动漂移 |
| frame | 目标在同源 iframe 内（已知盲区，用作**负例**） |

新增负例两条：`n04` 折叠面板没展开就想加购、`n05` 目标在 iframe 里点不到。
后者尤其关键——外层摆着一个同名倾向的按钮，硬凑的话很容易"成功"，而购物车
里其实什么都没有。**负例守的不是"能做"，是"做不到时不去点一个凑合的替代品"。**

扩面之后抓出的四个 bug（问题六~九，见 §2.2）对应的修法：

1. **分档名称匹配**（`browser_healing._rank_name_match` / `select_by_name`）：
   完全相等 > 元素名包含查询 > 查询包含元素名，同档取名字更短的。自愈换目标
   的候选池**只在同一档内轮换**——混入低档候选会让自愈越换越离谱。生产路径
   与兜底路径（`click_text` 的 `get_by_text(exact=False)`）一并修掉，跑分
   策略改为直接复用生产函数（两边口径不一致，量到的就不是同一个产品）。
2. **`<summary>` → `role=summary`**，另补 `contenteditable` → `textbox`。
3. **`collect_refs` 返回结构化 `CollectedRefs`**，canvas 盲区真正传出来；
   且**快照非空时也要提示**——画布页常配着几个真按钮，空快照分支根本不触发。
4. **测试隔离**：`test_builtin_browser_policy.py` 加 autouse fixture 把
   `_POLICY_FILE` 指到 tmp，并清掉了被污染的用户配置。

### 3.7 第三轮：把「成功是真成功」接到生产入口（2026-08-30）

对着核心任务逐条审计「文档声称的 vs 代码接上的」（§2.3）之后，补上最重
的一条：**生产路径此前没有结果校验器**。`require_change` 只能证明「页面
动了」，证明不了「动对了」——点了「加入购物车并结算」，页面当然也会动。

- **`expect` 结果校验闸**：`BrowserHealer.click/type_text` 新增
  `expect_text` 参数，编译成异步校验器接进 `orchestrator.execute` 的
  verifier 闸。点「加入购物车」并传 `expect_text="已加入购物车"`，看不
  到就判 F6 如实上报，而不是拿「changed=True」冒充成功。校验用
  `wait_for`（上限 4s）而不是立刻看，避免把延迟渲染的正常成功误判成失败
  ——那条闸门的信誉一旦坏了就没人再信它。
- **工具面暴露 `expect`**：`browser_act` 的点击/输入都接受 `expect`，
  写进参数描述里并明确「可选但强烈建议」——只有模型知道成功长什么样，
  口子不开到工具面，校验器就等于没接。
- **F6 阶梯去掉 REFRESH**（见 §2.3）：「结果不对」不能被刷新上下文伪装成
  「点了没反应」。

这一轮全程是**审计驱动**：先列「删掉它用户能感知吗」，再决定修什么，
而不是按功能清单推进。

### 3.8 第四轮：把自愈层里最后一处"猜"挖掉（2026-08-30）

第三轮留了一笔欠账：脏页面基线里 `d04`（400ms 整块重排页）靠 `retries=1`
绕过，根因记作"refresh 之后快照丢锚点，疑似窗口期 bug"。这一轮不猜——用
强制相位探针（刻意把快照→点击管道卡进重建边界，12+6 跑）把故障链完整录了
出来：

**抓到的东西比记录在案的更严重。** 旧代码在强制相位下产出 **3 起错品谎报**
（12 跑中 2 起、端到端 6 跑中 1 起）：目标是商品 p05，购物车里却是 p01/p07，
而驱动报 `ok=True`。路径是：

```
首击在重建边界失效 → 判 F5 → 旧 F5 阶梯含 SUBSTITUTE
→ substitute 拿失效的 ref 编号套到重排后的元素上取名「加入购物车」
→ 在 6 个同名按钮（各属于不同商品）里轮换 → 点到别的商品
→ 页面变了、驱动零报错 → 报成功          ← 静默失败 + 谎报
```

列表页上同名按钮个个是真的、各属于不同实体——"换同名候选"在这里不是自愈，
是拿别的实体冒充原目标。**上下文过期 ≠ 选错了**，与第三轮"够不着 ≠ 选错了"
是同一条纪律的另一面。

四处修复（全部实测复跑验证）：

1. **F5 阶梯去掉 SUBSTITUTE**（`orchestrator.py`）：改为 `(REFRESH, REPLAN,
   ESCALATE)`，与 F6 去 REFRESH、F8 去 SUBSTITUTE 同款"刻意不含"纪律，配
   元约束测试锁定。SUBSTITUTE 留给 F4（目标已被证明无效）专用。
2. **refresh 按名重映射加两条纪律**（`browser_healing._on_refresh`）：
   ref 路径的点击原本拿不到旧目标名字（`healer._snapshot` 为空，refresh 永远
   死路）——回退到会话最近一次快照找回名字；新快照里旧名字对应**多个**元素时
   拒绝重映射——无法确认哪个是原目标，挑一个就是谎报，不如实上报交给知道锚点
   的调用方。
3. **等待中途元素消失判 F5 不判 F4**（`browser._rethrow_if_stale`）：重排页
   会在点击等待半途抹掉注入属性，Playwright 的超时措辞（含 "waiting for" /
   "locator"）会被关键词分类误判成 F4"目标选错"，又触发同名轮换——同一条
   错路。执行层在超时后重查元素：没了就抛 `RefStaleError`（F5）。
4. **click_near 恢复重试**（`run_dirty.py`）：绕过用的 `retries=1` 作废，
   恢复为 3 次有界重试（编排层不再猜之后，"重新看一眼再点"才是正当恢复）；
   锚点不在视口快照时回退全页快照重新定位（失败点击的滚动/重排会把目标暂时挪
   出视口）；确定性失败（F8/F6/F7）不重试——重看不治的失败，重试只是烧超时。

**复跑数字**（真 Chromium，强制相位探针）：修复前错品 2/12 + 1/6 → **修复后
0/12 + 0/6**；探针期间出现的 4 次 F5 全部如实升级、再由锚点重新定位找回。
随附 `scroll_click_near`（叠加页合并步）端到端 6/6 全对。

这一轮的方法论与第三轮相同：**先证明问题真实存在（探针抓到错品），再修，再
复跑证明被消灭**。"应该修好了"不算数。

反向护栏是刻意的：一个把所有元素都标成 `obscured` 的实现照样能通过"能标
出来"的测试，一个禁止一切换目标的实现也照样能通过"不换目标"的测试——两种
都会让机制失去意义，所以每条正向断言都配一条反向断言。唯一同名时仍应重映射
成功（`test_healer_recovers_from_stale_ref`）、F4 的同名轮换仍应工作
（`test_healer_recovers_from_inert_target`），歧义护栏不许误伤这两条。

shim 的解释器即可全绿（全量 `tests/unit` 下同类删除用例共 14 条，均此因）。
