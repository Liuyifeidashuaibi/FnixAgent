# Blog Post 模板 / Blog Post Templates

> 写 FnixAgent 技术博客时的模板与最佳实践。

---

## 模板 1:技术深度文(1500-3000 字)

### 标题(SEO 友好)

```
<Title>: <Concrete Subtitle>

示例:
- "KTG/STP/MFP 三层任务图:让 Agent 第一次具备工程纪律"
- "为什么我把 LangChain 的 ConversationBufferMemory 换成 Git 仓库"
```

### 大纲

```markdown
## 背景与问题
- 我在做什么项目(1 段)
- 遇到了什么具体问题(1-2 段,故事化)

## 现有方案的不足
- 方案 A 及其问题
- 方案 B 及其问题
- 方案 C 及其问题

## 我的解决方案
### 核心思想(1 段,大白话)
### 技术细节(代码 + 架构图)
### 数据流图

## 评估
- 性能数据(before / after)
- 用户反馈
- 局限

## 学到的教训
- 3-5 条 bullet

## 接下来做什么
- 路线图
- 邀请讨论

## 参考链接
- ADR
- 相关项目
```

### 风格建议

- **第一人称**:讲"我怎么想 / 怎么做",不是"FnixAgent 如何如何"
- **代码 > 文字**:尽量贴代码 / 截图
- **失败展示**:踩过的坑要写,比成功更有教育意义
- **避免夸赞**:不要"完美""强大",用"在 X 场景下,Y 指标提升 N%"

## 模板 3:技术决策故事(1000-2000 字)

### 标题

```
我为什么从 X 换成 Y

示例:
- "我为什么从 LangChain 换成自研"
- "我为什么把 SQLite 换成 PostgreSQL 又换回来"
```

### 大纲

```markdown
## 起点
我在做 X 项目,需要 Y 能力。

## 第一版: 用了 A
A 看起来完美:
- 优点 1
- 优点 2

但用了一阵子发现:
- 问题 1(具体场景)
- 问题 2(具体场景)

## 转折
某个具体事件让我决定换。
(讲故事,带数据 / 截图)

## 第二版: 换成 B
为什么选 B:
- 理由 1
- 理由 2

短期阵痛:
- 代价 1
- 代价 2

## 结果
现在的数据:
- 性能: ...
- 维护性: ...
- 用户反馈: ...

## 给读者的建议
- 如果你也在选 X / Y,我的判断标准是:...
- 不要盲目跟我学,关键是:...

## 反思
- 当时如果选 B 会怎样?
- 当时如果坚持 A 会怎样?
```

### 风格建议

- **诚实**:承认错误决策,不要"完美先生"
- **数据**:用 benchmark / 错误率 / 用户反馈支撑
- **可推广**:不要只讲"我"的,要讲"为什么对你也重要"

## 模板 5:故障复盘(1000-2000 字)

### 标题

```
Postmortem: <具体故障描述>

示例:
- "Postmortem:agentd 在 macOS 14 上 OOM,损失 30% 用户 2 小时"
```

### 必须包含的章节(对齐 [INCIDENT-RESPONSE](../operations/INCIDENT-RESPONSE.md))

```markdown
## TL;DR
1-2 句话总结故障 + 影响。

## 时间线
| 时间 | 事件 |

## 影响
- 用户数
- 数据丢失
- API Key 泄露

## 根因分析 (5 Whys)
1. 为什么 X?因为 Y
2. 为什么 Y?因为 Z
3. 为什么 Z?...

## 修复
- 立即:回滚到 v0.4.3
- 短期:加 LRU 边界
- 长期:加集成测试覆盖

## 行动项
| 优先级 | 项 | 负责人 | 截止 |

## 学到的教训
- 不要 mock 真实资源
- LRU 必须有界
- macOS 14 必须实测

## 致谢
感谢谁第一时间反馈。
```

## 风格检查清单

提交前自检:

- [ ] 标题具体(不是"深度学习入门")
- [ ] 第一段就说清要解决什么问题
- [ ] 有具体数字(性能 / 用户数 / 错误率)
- [ ] 有架构图或截图
- [ ] 有可运行代码示例
- [ ] 失败与教训段落
- [ ] 引用具体 ADR / commit / PR 链接
- [ ] 文末有"接下来做什么"
- [ ] 末尾有 LICENSE 链接
