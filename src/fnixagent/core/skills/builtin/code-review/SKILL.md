# code-review — 代码审查

## 基本规则

- 问题定位一律用**新版本行号**（diff 右侧）；多行问题给 `[起始行, 结束行]`，单行两者相同
- 每个发现必须有仓库级证据支撑，禁止只看片段就下结论

## 执行步骤

### Step 1: 确定审查范围

- 用户指定了范围（某文件 / 某分支对比 / 某 MR）→ 照做，不扩大不缩小
- 未指定 → 询问用户，常见选项：① 当前未提交变更（`git diff`）② 对比某分支（`git diff <branch>`）③ 指定文件
- 用户让你直接开始 → 默认审查工作区未提交变更

### Step 2: 收集上下文（出结论前必做）

用 `run_command` 跑 git 探针 + `read_file`/`grep` 读代码：

1. `git status` — 工作区状态
2. `git diff --name-only` — 变更文件面
3. `git diff` — 权威变更内容（聊天里贴的片段仅供参考，以 diff 为准）
4. 读被改文件的**完整**内容及调用链邻居，定位既有的校验/工具函数

### Step 3: 推断作者意图

把 diff 当整体分析，从改动模式推断意图（加错误处理→防御性重构；换算法→行为变更，查调用方不变量；依赖升级+适配→API 迁移，查旧安全假设；重命名→语义变化小）。形成一句话意图摘要，作为后续判断的上下文与决胜依据。

### Step 4: Mermaid 变更概览

**必须**提供至少 1 张 mermaid 图总结关键变更（复杂变更 2 张：业务流 + 技术流）：

- 优先 `flowchart` / `sequenceDiagram`，展示**真实的逻辑链/调用序列/数据流**；禁止只分类不表达关系的静态盒子图
- 只画关键变更，不画整个系统；变更节点用高对比配色标出，**fill 和 color 都要指定**（如 `fill:#c8e6c9,color:#1a5e20`），保证明暗主题都可读

### Step 5: 问题清单

按严重度分级输出，每条含：位置（文件+新版行号区间）、严重度、问题描述、为什么是问题、建议方向：

| 级别 | 判据 |
|---|---|
| Critical | 正确性错误、数据丢失、安全漏洞、崩溃路径 |
| Major | 逻辑边界缺陷、资源泄漏、并发隐患、明显性能退化 |
| Minor | 可读性、命名、重复代码、缺失测试 |
| Nit | 风格偏好，可不改 |

原则：
- 只报**这次 diff 引入或触碰**的问题；既有历史债标注「既有问题」单列
- 与推断意图矛盾的发现需要更强证据，不是更弱
- 不确定的用「疑似」明确标注置信度；测试/fixture 代码里的问题默认不报
- 结尾给一段总体评价：意图达成度、可合并性结论（可合并 / 小改后可合并 / 需要重做）
