# debugging — 证据驱动调试

## 核心哲学

用**科学方法**调试：先提出多个可证伪的假设，再通过最小插桩收集运行时证据，证据明确指向根因后才做最小修复，最后用「修复前 vs 修复后」日志对比证明问题解决。目标是消灭「凭感觉猜着改」。

## 强制启动协议（调试任务的第一个回复必须包含）

1. **禁改业务逻辑**：拿到运行时证据前，严禁修改任何业务逻辑代码
2. **生成会话 ID**：按 bug 描述起语义化 ID（小写英文+连字符，2-4 词，如 `login-500-error`）
3. **初始化调试记录**：在工作区创建 `.fnix/debug/debug-<sessionId>.md`，作为本次调试的第一个写操作，记录：症状、假设清单、插桩点、证据、结论
4. **公开假设**：在对话中列出 3-5 个**可证伪**的假设，每个假设对应一个具体观察点
5. **插桩优先**：对既有代码的第一个 Diff 必须且只能是插桩日志

## 证据门（不可协商）

- 假设必须靠插桩日志验证，不能只靠读代码；「显而易见」的 bug 也要证据确认
- 第一个代码改动必须是插桩，不是修复尝试
- 证据不足时补插桩，不猜

## 插桩规则

- 用带统一前缀的结构化日志（如 `[DBG:<sessionId>:<point-id>]`），输出到 stderr 或日志文件，便于 grep 提取
- 所有插桩包在 `#region debug-point <id>` / `#endregion` 注释块内，方便一键清理
- 最小侵入：不在业务代码库新建工具文件，用内联单行
- 每个插桩点对应一个假设的观察点，记录进 debug-<sessionId>.md

## 工作流

1. **观察与假设**：收集症状（实际 vs 预期）、复现步骤、环境、既有日志/堆栈 → 列 3-5 个假设
2. **插桩**：写入观察点，向用户说明改了什么、如何复现（给出具体操作路径），交还回合
3. **复现与采集**：用户复现（或用 run_command 自动复现）后读取日志
4. **证据裁决**：引用具体日志行，逐条标注假设的 证实/证伪 状态；全部证伪则补充假设重新插桩
5. **最小修复**：证据明确指向根因后，做最小范围修复
6. **对比验证**：再次运行，展示 pre-fix vs post-fix 日志对比证明修复且未引入新问题
7. **确认门**：向用户明确询问（A 已修复 / B 仍复现 / C 症状变化需继续 / D 中止调试）；**用户确认前禁止清理**
8. **清理**：用户确认 A 或 D 后，删除所有 `#region debug-point` 插桩、调试记录归档，输出根因总结

## 输出要求

- 每次插桩/修复后：变更摘要 + 用户操作指引（怎么复现、看哪里）
- 分析报告引用具体日志行，不空谈
- 修复方案附最小 Patch + 前后对比结论
- 任何检查点都提供「中止调试」选项，选中即清理并总结进展
