# security-review — 安全审查

## 铁律（违反任意一条的发现必须丢弃）

1. **只用新版行号**（diff 右侧），范围形式 `[起始行, 结束行]`
2. **只审本次 diff 引入或触碰的面**；变更前就存在且未被触碰的弱点超出范围
3. **可报告 ⇔ 可论证利用**：说不清 (a) 攻击者可控输入从哪进入、(b) 到达哪个危险 sink 或边界，就不报
4. **置信度下限 0.8**：低于就丢弃或标注移交人工复核
5. **不写补丁**：识别并解释，不在报告里写替换代码
6. 默认排除：可用性/DoS、限流、代码风格、测试/fixture 代码内的问题

## 流程

### 1. 范围确认

用户指定范围照做；缺失或模糊时询问（① 工作区未提交变更 ② 对比某分支 ③ 某 MR ④ 指定文件列表）；用户让直接开始 → 审 `git diff`（工作区）。

### 2. Diff 数据采集（git 探针）

用 `run_command` 依次跑：`git status` → `git diff --name-only` → `git log`（重建多提交意图）→ `git diff`（**唯一权威变更内容**）。探针失败按级联降级：`git diff origin/HEAD...` → `git diff HEAD~1` → `git diff` → 询问用户。

### 3. 上下文取证（出结论前必做）

禁止只看片段推理。每个候选发现必须收集：

- **Source 侧证据**：执行路径上具体的攻击者可控入口（HTTP 参数、文件内容、环境变量、外部 API 响应…）
- **Sink 侧证据**：输入到达的危险操作（SQL 拼接、命令执行、路径拼接、反序列化、eval、模板注入、越权数据访问…）
- **旁路上下文**：附近代码是否已有清洗/编码/校验/鉴权；项目既有的 sanitizer 工具是否已消解该问题

Source 或 Sink 任一无法从仓库代码证实 → 丢弃该发现。

### 4. 作者意图重建

从改动模式推断意图（新增错误处理→防御性重构，「缺校验」类发现要提高证据门槛；依赖升级→检查旧安全假设是否仍成立）。与明确防御意图矛盾的发现需要更多证据。

### 5. 报告格式

每条发现：

```
[严重度] 漏洞类别 — 文件路径 [L_start, L_end]（置信度 0.x）
- Source: <攻击者输入入口 + 行号>
- Sink: <危险操作 + 行号>
- 路径: <source 到 sink 的传播链，标出中途缺失的防护点>
- 影响: <被利用后果>
```

严重度：Critical（可远程利用/数据泄露）/ High（需要一定前置条件）/ Medium（利用链较长或影响受限）。结尾汇总：审计范围、探针输出摘要、发现数、无发现时明确声明「本次变更面未发现可论证利用的漏洞」而非泛泛的「代码安全」。
