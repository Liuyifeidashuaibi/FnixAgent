# doc-writing-guide — 写作总控

## 1. 动笔前先解读意图

理解请求的**精神**而非字面。收到写作任务先分析：

1. **目的**：告知 / 说服 / 教学 / 娱乐 / 售卖 / 存档
2. **读者**：高管 / 工程师 / 大众 / 领域专家 / 学生
3. **语气**：正式 / 口语 / 权威 / 活泼 / 克制
4. **范围**：快速草稿 / 精修交付物 / 迭代共创
5. **约束**：字数、语言、格式、品牌要求

据此大胆采用最合适的写作人格（犀利评论员 / 耐心教师 / 冷静分析师…），不要默认平庸安全的中性文风。用户偏好不明时默认**内容丰富、结构完整**，除非明确要求简短。

只在歧义会导致**根本不同的交付物**时才提问澄清；小的不确定做合理假设、声明后继续。

## 2. 体裁与参照系

| 体裁      | 触发词             | 特征                         |
| --------- | ------------------ | ---------------------------- |
| 学术/研究 | 论文、综述         | 正式、有据、分节、引用       |
| 技术文档  | docs、API、README  | 精确、任务导向、代码示例     |
| 博客/文章 | 博客、文章、写一篇 | 引人的开头、口语化、可有观点 |
| 教程      | 教程、指南、怎么做 | 渐进披露、动手实操           |
| 营销文案  | 落地页、文案、宣传 | 利益导向、精炼、有 CTA       |
| 需求文档  | PRD、需求、规格    | 结构化、无歧义、验收标准     |
| 备忘/简报 | 备忘、简报、汇总   | 直接、行动导向               |

为目标体裁找参照系（如技术深挖对齐 Stripe 工程博客的清晰递进、商业分析对齐 HBR 的分析严谨+平实语言），作为**灵感**融合改造，不是照抄。

## 3. 交付格式路由（默认规则）

报告类任务（研究报告、白皮书、PRD、方案、竞品分析、可行性、技术文档等结构化书面交付物）：

> **默认 → html-report 技能**。仅当用户**明确**说要 .docx / Word → 走 docx 技能；明确说 .pdf → 走 pdf 技能。「写个报告」「起草 PRD」这类没提格式的请求一律 html-report。

演示/幻灯片 → html-deck 技能。纯 Markdown 短文（备忘、README、说明）直接写 .md 到 `.fnix/artifacts/`。

## 4. 语言禁区

- 禁止清单式企业黑话填充：「可落地」「可执行清单」「30 天行动计划」「每周复盘」「actionable checklist」，禁止把人类体验包装成可优化的工作流
- 禁止空泛套话开头（「在当今快速发展的时代…」）；直接进入主题
- 重要论断要有支撑（数据/例子/推理），每段推进论证

## 5. 质量自检

- 全文与用户语言一致；术语前后统一
- 标题层级清晰（H2 章 / H3 节）；长文有目录
- 读者读完能回答「这文档要我知道什么/做什么」
