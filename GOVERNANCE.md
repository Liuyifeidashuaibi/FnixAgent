# Governance

This document describes how the FnixAgent project makes decisions, who has merge rights, and how contributors can take on more responsibility.

> 📌 **TL;DR:** FnixAgent is a **benevolent-dictatorship-with-layers** project. Day-to-day decisions are made by the **Lead Maintainer**. Significant changes require a **maintainer review** and are tracked in the public [ROADMAP.md](ROADMAP.md).

---

## Roles

### 🧑‍🚀 Lead Maintainer (BDFL-delegate)

- **Current:** [@Liuyifeidashuaibi](https://github.com/Liuyifeidashuaibi)
- Sets project vision, releases, and final tie-breaker on contentious decisions.
- Owns the public roadmap, security disclosures, and external communications.
- Step-down process: announce in [Discussions → Announcements](https://github.com/Liuyifeidashuaibi/FnixAgent/discussions/categories/announcements) ≥ 30 days before handing off; nominate a successor.

### 🛠️ Maintainers

- Have **write access** to the repository.
- Triage and merge PRs, cut releases, and respond to security reports.
- Listed in [MAINTAINERS.md](MAINTAINERS.md).
- Promoted from **Reviewers** by unanimous maintainer vote + lead approval.

### 🔍 Reviewers

- Have **Triage** access (apply labels, close issues, mark duplicates).
- Are expected to review PRs in their domain within 7 days.
- Promoted from **Active Contributors** by any maintainer nomination + 1-week comment period.

### 🌱 Active Contributors

- ≥ 3 merged PRs OR ≥ 10 substantive issue/discussion interactions in the last 6 months.
- Listed in the next release's [CHANGELOG.md](CHANGELOG.md) under "Contributors".
- Receive priority review on new PRs.

### 🤝 Contributors

- Anyone who has opened a merged PR.
- Welcome to keep contributing — see [CONTRIBUTING.md](CONTRIBUTING.md).

## Decision-making

| Decision type | Process |
|---------------|---------|
| Bug fixes, refactors, docs | Maintainer review + 1 approval |
| New feature (small) | RFC or issue discussion + 1 maintainer approval |
| New feature (large / breaking) | RFC, ≥ 1 week public comment, ≥ 2 maintainer approvals |
| Public API change | RFC + lead approval |
| Security fix | Private process per [SECURITY.md](SECURITY.md), backported to all supported releases |
| License change | Unanimous maintainer approval + community notice ≥ 30 days |
| Governance change | This document, ≥ 2-week comment period, lead approval |

We use **lazy consensus**: if a PR has been open for 7 days with no objections from a maintainer, and CI is green, a maintainer may merge.

## Release process

1. Cut a release branch from `main` following [RELEASE.md](RELEASE.md).
2. Run the full release gate (`pnpm verify:beta && pnpm gate:*`).
3. Publish artifacts via the `release.yml` GitHub Actions workflow.
4. Draft release notes are auto-generated by `release-drafter.yml`.
5. Lead maintainer signs off on the GitHub Release before publishing.

See [RELEASE.md](RELEASE.md) for the full cut-train-ship procedure.

---

## Conflict resolution

1. Discuss on the relevant PR/issue with civility (per [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md)).
2. If unresolved, escalate to a private maintainer thread.
3. Lead maintainer casts the final binding vote.
4. Disputes about process (not technical merit) can be appealed by opening a [meta issue](https://github.com/Liuyifeidashuaibi/FnixAgent/issues/new?template=blank.md) labeled `meta`.

---

## Becoming a maintainer

There is no formal application. We promote people who:

- Have shipped high-quality contributions over **at least 3 months**.
- Have demonstrated good judgment in code review.
- Are kind and constructive in community interactions.
- Can dedicate a few hours per week to triage and review.

Nominations happen in a private maintainer thread and require lead approval.
