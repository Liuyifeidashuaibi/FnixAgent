0核心结论速览

三句话结论

  1. 前端、后端、Agent 评测是三条独立的测试线，分别验证「UI 渲染与交互」「API 契约与业务逻辑」「AI 决策与工具调用质量」，通过集成测试在 API 边界汇合，而非在 UI 层强行打通。
  2. Agent 评测必须通过 API（FastAPI 端点）进行，不通过 UI。所有主流 Benchmark（SWE-bench、AgentBench、DeepEval）都是 API/CLI 接入——因为 Agent 评测需要可复现、可批量、可自动判分，UI 自动化会引入非确定性噪声。
  3. 前端 UI 全量 E2E 不是必须的。开发模式下前端就是 Vite Web 服务（localhost），React 组件测试用 vitest + Testing Library 覆盖绝大多数场景；只在「跨 Tauri IPC 边界的关键用户流」上用 tauri-driver 做少量冒烟级 E2E。
静态检查 TypeScript+Clippy+Ruff 单元测试 vitest / pytest / cargo test 集成测试（主力层） Agent 评测 DeepEval（API 接入） E2E tauri-driver（少量冒烟）
测试线 主要工具 测什么 接入方式 占比建议
前端 vitest + Testing Library 组件渲染、交互逻辑、状态管理 jsdom（不开浏览器） ~30%
后端 API pytest + httpx 端点契约、业务逻辑、错误处理 直接调 FastAPI ~30%
Rust 命令 cargo test Tauri Command 逻辑、状态管理 原生 Rust 测试 ~10%
Agent 评测 DeepEval / 自建 EvalRunner 任务完成度、工具调用、规划质量 FastAPI 端点（API） ~25%
E2E 冒烟 tauri-driver + WebdriverIO 关键用户流、IPC 边界 真实 Tauri 应用 ~5%

1测试金字塔模型

1.1 经典测试金字塔（Mike Cohn, 2009）

Mike Cohn 在《Succeeding with Agile》中提出测试金字塔，将自动化测试分为三层，每层宽度与测试数量成正比：

图 1：经典测试金字塔 — 底宽顶窄，数量从多到少

  • 单元测试（底层，~70%）：测试单个函数/类/方法的行为，不依赖外部组件，可在数秒内运行数千个。
  • 集成测试（中层，~20%）：验证多个组件协作（如代码与数据库、API 检索），关注组件间的接口边界。
  • 端到端测试（顶层，~10%）：启动完整应用模拟真实用户操作（点击、输入、断言 UI），最全面但最慢、最贵、最难维护。

来源：Mike Cohn《Succeeding with Agile》(2009)；Ham Vocke "Test Pyramid" (martinfowler.com)

1.2 Testing Trophy 模型（Kent C. Dodds）

Kent C. Dodds 针对现代前端应用提出 Testing Trophy，核心主张是"写最多的集成测试"，而非最多的单元测试。他认为测试的目标不是覆盖率，而是信心（confidence）：

图 2：Testing Trophy — 集成测试最厚，单元和 E2E 较薄

层级 工具示例 验证什么 信心 / 成本比
静态 TypeScript / ESLint / Clippy / Ruff 类型错误、语法、编码规范 极低成本捕获低级错误
单元 vitest / pytest / cargo test 单一函数/纯逻辑的输入输出 快但信心有限（隔离了上下文）
集成 Testing Library / httpx 多组件协作、真实边界交互 最佳信心/成本比
E2E Playwright / tauri-driver 完整用户流的端到端验证 信心最高但成本也最高
Dodds 的关键洞察："写测试是为了获得对代码的信心，而非追求覆盖率数字。" 集成测试在"覆盖真实交互"与"维护成本"之间取得了最佳平衡——它不像单元测试那样过度隔离（失去上下文真实性），也不像 E2E 那样需要启动整个系统（太慢太贵）。

来源：Kent C. Dodds "Static vs Unit vs Integration vs E2E Testing" (kentcdodds.com)；"The Testing Trophy and Testing Classifications" (kentcdodds.com)

1.3 Testing Honeycomb（Spotify 蜂巢模型）

Spotify 工程团队针对微服务架构提出蜂巢模型，指出传统金字塔在微服务下"崩塌"——因为服务间依赖不可控、测试环境不稳定、变更影响范围大。蜂巢模型将集成/契约测试进一步加厚，单元测试层变薄：

  • 单元测试层（薄）：只测纯函数和独立模块，不追求 70% 的夸张比例。
  • 集成 / 契约测试层（最厚）：服务间接口契约、组件组合验证是核心。
  • 端到端测试层（薄）：只保留关键路径的冒烟测试。

对于 FnixAgent 这类多后端架构（Rust + Python + React 三条技术栈），蜂巢模型的思路比经典金字塔更适用——因为三栈之间的"接缝"（IPC 边界、HTTP 边界）恰恰是 Bug 高发区，需要重点用集成测试覆盖。

来源：Spotify Testing Honeycomb；综述见 engineering.atspotify.com（微服务测试实践）

1.4 桌面应用的特殊考虑

桌面应用与纯 Web 应用相比，测试多了以下维度：

差异点 Web 应用 桌面应用（Tauri）
运行环境 浏览器（标准统一） 原生 WebView（Windows=WebView2, macOS=WKWebView, Linux=WebKitGTK），行为有平台差异
后端 远程服务器 本地 Rust 进程（Tauri Command 通过 IPC 调用）
系统能力 受浏览器沙箱限制 文件系统、剪贴板、系统通知、全局快捷键等原生 API
分发形态 始终是 Web 服务 打包为原生可执行文件（.exe/.dmg/.deb）
更新机制 服务端部署即更新 需要 updater 插件和版本管理

这意味着桌面应用额外需要测试：跨平台 WebView 一致性、Tauri IPC 通信、原生 API 调用、打包后行为。

2各层测试的具体做法

2.1 单元测试：各语言各测什么

Python 端（pytest）— FastAPI / LangGraph 后端

测什么 示例 不测什么
纯函数 / 工具函数 prompt 模板拼接、参数校验、配置解析 实际 LLM 调用（用 mock）
数据模型 / 序列化 Pydantic 模型校验、枚举转换 数据库实际读写
LangGraph 节点纯逻辑 状态转换函数、条件路由判断 完整 Graph 执行（放集成）
解析 / 转换逻辑 工具调用结果解析、JSON 提取 外部 API 真实请求 
# tests/test_tools.py
def test_parse_tool_result_valid_json():
    raw = '{"status": "ok", "data": [1, 2, 3]}'
    result = parse_tool_result(raw)
    assert result["status"] == "ok"
    assert result["data"] == [1, 2, 3]

React 前端（vitest）— 组件与逻辑

测什么 示例 不测什么
纯逻辑 / hooks useDebounce、useLocalStorage、状态 reducer 样式 / 视觉外观
工具函数 格式化、日期处理、权限判断 第三方库内部行为
简单组件（无副作用） Button 渲染 props、Badge 条件显示 组件 + API 组合（放集成）

Rust 端（cargo test）— Tauri 后端

测什么 示例 不测什么
Tauri Command 纯逻辑 文件路径处理、配置读写逻辑、状态管理 完整 Tauri 应用启动
数据处理 序列化 / 反序列化、数据转换 WebView 渲染
跨平台条件编译 #[cfg(target_os)] 分支逻辑 原生 OS API 实际调用 
// src-tauri/src/commands.rs
#[cfg(test)]
mod tests {
    #[test]
    fn test_sanitize_path_rejects_traversal() {
        assert!(sanitize_path("../../etc/passwd").is_err());
        assert!(sanitize_path("data/config.json").is_ok());
    }
}

单元测试的共同原则

  • 不依赖外部服务：LLM、数据库、文件系统都用 mock 或 fixture。
  • 快：数千个测试在数秒内跑完，作为开发时的即时反馈。
  • 隔离：一个测试失败不应导致其他测试级联失败。
  • 确定性：相同输入永远相同输出，不依赖时间/随机/网络。

2.2 集成测试：API 端点 + 组件交互

集成测试是 Testing Trophy 和蜂巢模型共同推荐的主力层，验证"多个组件协作时是否正确"。

后端 API 集成测试（pytest + httpx / TestClient）

# tests/test_api_integration.py
from fastapi.testclient import TestClient
from app.main import app
from unittest.mock import AsyncMock, patch

client = TestClient(app)

def test_chat_endpoint_returns_stream():
    with patch("app.routes.chat.run_agent") as mock_run:
        mock_run.return_value = AsyncMock()
        mock_run.return_value.__aiter__.return_value = iter([
            {"type": "token", "content": "Hello"},
            {"type": "done", "content": ""}
        ])
        response = client.post("/api/chat", json={"message": "hi"})
        assert response.status_code == 200
        assert "Hello" in response.text

def test_tool_call_endpoint_validates_params():
    response = client.post("/api/tools/call", json={"tool": "", "args": {}})
    assert response.status_code == 422  # 参数校验失败

测什么：端点契约（请求/响应格式、状态码、错误处理）、中间件链（鉴权、限流、日志）、LangGraph 编排（mock 掉 LLM，验证节点流转和状态转换）。

前端组件集成测试（vitest + Testing Library）

// src/__tests__/ChatPanel.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { ChatPanel } from "../components/ChatPanel";

// mock 掉 API 调用，验证组件 + mock API 的交互
jest.mock("../api/client", () => ({
  sendMessage: jest.fn().mockResolvedValue({ reply: "你好" }),
}));

test("用户输入消息后显示回复", async () => {
  render(<ChatPanel />);
  await userEvent.type(screen.getByPlaceholderText("输入消息"), "你好");
  await userEvent.click(screen.getByRole("button", { name: "发送" }));
  expect(await screen.findByText("你好")).toBeInTheDocument();
});

测什么：组件 + API mock 的交互、用户操作流（输入→点击→断言结果）、状态流转（loading→success→error）。这里不打开真实浏览器，用 jsdom 模拟 DOM。

2.3 E2E 测试：Playwright / tauri-driver / Cypress

工具 适用场景 能否测 Tauri 特点
tauri-driver + WebdriverIO Tauri 原生应用 E2E（官方推荐） 是（首选） 驱动原生 WebView，可测 Tauri IPC
Playwright 纯 Web 前端 E2E 部分（仅 dev 模式前端） 跨浏览器、auto-wait、并行快
Cypress 纯 Web 前端 E2E 部分（仅 dev 模式前端） 开发体验好，但仅 Chromium 内核

关键区分

Playwright / Cypress 只能驱动「浏览器」，无法驱动 Tauri 的原生 WebView 窗口，也无法测试 Tauri IPC（invoke()）、系统通知、文件对话框等原生能力。要测真正的 Tauri 应用，必须用 tauri-driver（WebDriver 协议）+ WebdriverIO。

2.4 前端 UI 测试：何时真正打开浏览器

这是最关键的实践判断——大部分前端测试不需要打开浏览器：

场景 需要打开浏览器吗 用什么
组件渲染、props 传递、条件显示 不需要 vitest + jsdom
用户交互流（输入、点击、表单提交） 不需要 vitest + Testing Library + jsdom
组件 + API mock 的集成 不需要 vitest + MSW（mock service worker）
样式 / 视觉回归 / 布局 需要 Playwright 截图对比 / Percy
跨 WebView 平台一致性 需要 tauri-driver
Tauri IPC / 原生 API 交互 需要 tauri-driver（唯一选择）
关键用户流端到端冒烟 需要 tauri-driver
Dodds 原则的延伸应用："如果你能用更低层级的测试获得同样的信心，就不要用更高层级的。" 打开浏览器是最贵的操作——启动慢、易 flaky、调试难。jsdom 已能模拟 95% 的 DOM 行为，只有真正依赖浏览器引擎或原生平台能力的测试才需要开浏览器。

3Tauri 应用的特殊测试方式

3.1 Tauri 官方推荐：tauri-driver + WebDriver

Tauri 官方推荐使用 tauri-driver，它是一个实现了 WebDriver 协议的代理，将 WebDriver 命令转发给各平台的原生 WebView 驱动：

平台 原生 WebView WebDriver 驱动
Windows Microsoft Edge WebView2 msedgedriver.exe
macOS WKWebView (Safari 内核) 系统内置 safaridriver
Linux WebKitGTK WebKitWebDriver

图 3：tauri-driver 架构 — WebdriverIO → tauri-driver → 平台原生驱动 → WebView

WebdriverIO 官方提供 @wdio/tauri-service，自动化了驱动发现、应用启动、跨平台二进制检测： 

# 安装
npm install --save-dev @wdio/tauri-service
# 可选：更丰富的 webview 内集成（mock IPC、执行 Tauri 命令）
npm install --save-dev @wdio/tauri-plugin
// wdio.conf.ts
export const config = {
  services: [["tauri", {
    app: "src-tauri/target/release/fnix-agent",  // 构建产物
  }]],
  capabilities: [{
    "tauri:options": { application: "src-tauri/target/release/fnix-agent" },
  }],
};

// 测试：验证 Tauri 应用窗口标题
describe("FnixAgent", () => {
  it("应显示正确标题", async () => {
    const title = await browser.getTitle();
    expect(title).toBe("FnixAgent");
  });
  it("用户可发送消息并获得回复", async () => {
    await $(".chat-input").setValue("你好");
    await $(".send-btn").click();
    await expect($(".chat-reply")).toBeDisplayed();
  });
});

WebdriverIO for Tauri 的优势：自动配置 WebDriver 层、跨平台、可选 @wdio/tauri-plugin 提供更丰富的 in-webview 集成（browser.tauri.execute、mock IPC）、deeplink / protocol handler 测试、Rust + 前端日志转发到测试报告。

来源：Tauri 官方测试文档 tauri.app/develop/tests/webdriver；WebdriverIO Tauri webdriver.io/docs/desktop-testing/tauri

3.2 开发模式 vs 生产模式的测试差异

Tauri 在两种模式下前端加载方式不同，直接影响测试策略：

开发模式（tauri dev） 生产模式（tauri build）
前端来源 Vite Dev Server（localhost:5175 等） 打包后的静态文件（frontendDist）
加载方式 Tauri WebView 从 devUrl 加载 Tauri WebView 从本地文件系统加载
Tauri IPC 可用（Rust 后端已启动） 可用（完整应用）
热更新 有（HMR） 无
适用测试 前端组件/集成测试（vitest） 完整 E2E（tauri-driver）

开发模式下能否直接用浏览器自动化测？

可以测前端 UI，但有重要限制：

  • 能测的：React 组件渲染、CSS 样式、用户交互流——因为前端就是标准 Vite Web 应用，Playwright / Cypress 可以直接打开 localhost:5175 操作。
  • 不能测的：所有 invoke() Tauri Command 调用会失败——因为普通浏览器没有 Tauri 的 IPC 桥接（window.__TAURI__ 不存在）。文件对话框、系统通知、全局快捷键等原生能力也无法在普通浏览器中触发。

结论：开发模式下用浏览器自动化测前端 UI 是可行的（用于样式/交互回归），但无法覆盖 Tauri 集成边界。要测完整的"前端调 invoke → Rust 处理 → 返回结果"链路，必须用 tauri-driver 驱动真实的 Tauri 应用。

推荐的分层策略

  1. 日常开发：vitest + jsdom（不开浏览器）覆盖组件逻辑和交互——快、稳、可频繁运行。
  2. 视觉回归：Playwright 打开 localhost:5175 截图对比——验证样式不被破坏。
  3. 关键路径 E2E：tauri-driver 驱动生产构建（tauri build 产物）——验证 Tauri IPC、原生能力、完整用户流。只在 CI 或发布前运行少量用例。

4AI Agent 应用的专项测试

4.1 Agent 评测 vs 传统软件测试的本质区别

维度 传统软件测试 AI Agent 评测
输出确定性 相同输入 → 确定输出（可精确断言） 相同输入 → 非确定输出（LLM 每次可能不同）
断言方式 精确匹配（assert x == 5） 模糊匹配 / LLM-as-judge（语义相似度、维度打分）
失败模式 崩溃、异常、错误值 规划出错、工具调用参数错、多轮遗忘、幻觉
测试对象 代码路径 / 函数行为 决策轨迹（trajectory）：一系列推理 + 工具调用 + 状态流转
可复现性 高（确定性） 低（需多次运行取统计分布）
质量标准 通过 / 失败（二值） 多维度评分（0-1 连续分数 + 原因解释）
核心区别：传统测试验证"代码是否按预期执行"，Agent 评测验证"AI 是否做出了正确决策"。前者是确定性逻辑验证，后者是非确定性智能行为评估。这决定了 Agent 评测需要全新的指标体系、判分方法和测试基础设施。

4.2 为什么 Agent 评测通常通过 API 而不是 UI

所有主流 Agent Benchmark 都通过 API / CLI 接入，没有通过 UI 的：

Benchmark 接入方式 判分方式 为什么不走 UI
SWE-bench Agent 通过 API 生成代码 patch 运行测试用例，检查 patch 是否通过 CI（resolve rate） 需要可复现的 Docker 沙箱；只读取 model_patch 字段，不关心 UI 交互
AgentBench Agent 通过 API 与 8 个环境交互（OS/DB/KG/Web 等） 多轮交互后的任务完成率 多轮交互需要精确控制；UI 自动化引入非确定性
DeepEval Pytest 原生，调用 Agent 的 Python API LLM-as-judge + 统计指标，多维度评分 需要捕获完整执行 trace；CI/CD 集成；批量运行
ToolBench Agent 通过 API 调用工具 工具选择准确率 + 参数准确率 需要精确控制工具调用；结构化输入输出

Agent 评测走 API 的四大理由

  1. 可复现性：Agent 输出本身已非确定，UI 自动化（渲染时序、动画、异步加载）会叠加更多非确定性，使结果无法复现。API 调用是同步的、结构化的、可精确控制的。
  2. 可自动判分：Benchmark 需要自动判断"任务是否完成"——SWE-bench 跑测试用例、AgentBench 检查环境最终状态、DeepEval 用 LLM-as-judge 评分。这些都依赖结构化输出，UI 只能给截图让人看。
  3. 批量与效率：Agent 评测通常需要跑数百个测试用例、每个多次运行取分布。API 调用比 UI 操作快 10-100 倍，且可并行。
  4. Trace 捕获：Agent 评测需要分析完整决策轨迹（每一步的推理、工具调用、参数）。API 层可以精确捕获每个中间状态；UI 层只能看到最终渲染结果，丢失了轨迹信息。

来源：SWE-bench (github.com/SWE-agent, NeurIPS 2024)；AgentBench (github.com/THUDM/AgentBench, ICLR 2024)；DeepEval (github.com/confident-ai/deepeval)

4.3 LLM 应用的评测维度

DeepEval 提供了业界最完整的 Agent 评测指标体系，分为轨迹级（Trajectory）和组件级（Component）两类：

类别 指标 评估什么 是否需要 Trace
轨迹级 Task Completion（任务完成度） Agent 是否成功完成了用户的目标 是
Step Efficiency（步骤效率） 是否有多余 / 冗余步骤 是
Plan Adherence（规划遵循度） 是否按照生成的计划执行 是
Plan Quality（规划质量） 生成的计划是否逻辑完整、高效 是
组件级 Tool Correctness（工具正确性） 是否选对了工具 否（单步）
Argument Correctness（参数正确性） 工具调用参数是否正确 否
Tool Use（工具使用质量） 工具使用的综合质量 否
Goal Accuracy（目标达成精度） 多大程度达成了预期目标 否

图 4：Agent 评测维度 — 轨迹级评估整体决策链，组件级评估单步工具调用

Thoughtworks Technology Radar（2026 年 4 月）已将 DeepEval 列为 Trial（试验采用）级别，确认其在 RAG、Agentic workflow、多轮对话评测方面的成熟度，并特别提到它支持与 MCP 服务器的交互评测。

来源：DeepEval 指标文档 deepeval.com/docs/metrics-introduction；Thoughtworks Technology Radar thoughtworks.com/radar · DeepEval

4.4 Agent 评测的 5 类典型问题

结合 FnixAgent 已有的 ProblemDetector 经验和业界共识，Agent 评测需重点检测以下 5 类问题：

# 问题类型 表现 对应评测指标 检测方法
1 规划出错 Agent 制定的计划逻辑错误、遗漏关键步骤、步骤顺序混乱 Plan Quality / Plan Adherence 对比预期计划模板；LLM-as-judge 评估计划合理性
2 工具调用参数错 选对了工具但参数格式错、值错、必填参数缺失 Tool Correctness / Argument Correctness Schema 校验；对比 expected args；执行后结果校验
3 忘记回退 工具调用失败后不重试 / 不换策略，直接放弃或继续错误路径 Step Efficiency / Task Completion 检测失败后是否有回退/重试 trace；分析轨迹中断点
4 多轮中断 长对话中丢失上下文、忘记前置约束、重复已完成步骤 Goal Accuracy / Plan Adherence 多轮测试用例；状态一致性检查；上下文保留检测
5 MCP 调用失败 MCP 协议握手失败、工具发现出错、序列化/反序列化错误 Tool Use / Task Completion MCP 服务器 mock；协议层单元测试；端到端 trace 检查

FnixAgent 已有的基础

根据项目记忆，FnixAgent 已构建自研 Agent 评测工具（tests/agent_eval/），含 TraceCollector + ProblemDetector + EvalRunner + ReportGenerator 四模块，22 项测试用例覆盖 8 类场景，通过率 86.4%。这与 DeepEval 的指标体系高度对应——建议后续可直接对接 DeepEval 的 TaskCompletenessMetric、ToolCorrectnessMetric 等标准化指标，补充 LLM-as-judge 能力，减少自维护判分逻辑的负担。

5结论：FnixAgent 应该怎么分层测试

5.1 推荐的四层测试架构

综合 Testing Trophy（集成为主）+ 蜂巢模型（接口边界为主）+ Agent 评测（API 接入）+ Tauri 特殊性（tauri-driver），FnixAgent 应采用以下四层架构：

图 5：FnixAgent 四层测试架构 — 集成层最厚，Agent 评测独立成线，E2E 最薄

5.2 各层工具与内容明细

层 技术栈 工具 测什么 运行频率
第一层
单元 + 静态 		React vitest + TypeScript hooks、纯函数、简单组件 每次提交
Python pytest + Ruff 纯函数、Pydantic 模型、解析逻辑、LangGraph 节点纯逻辑 每次提交
Rust cargo test + Clippy Tauri Command 纯逻辑、路径处理、状态管理、序列化 每次提交
第二层
集成（主力） 		前端↔API vitest + Testing Library + MSW 组件 + mock API 的用户流、状态流转、错误处理 每次提交

第三层
Agent 评测 		AI Agent DeepEval + 自建 EvalRunner 任务完成度、工具调用正确性、规划质量、5 类典型问题 每日 / 每次模型变更
第四层

5.3 Agent 评测应该通过 API 还是 UI

明确结论：通过 API（FastAPI 端点）

FnixAgent 的 Agent 评测应直接调用 FastAPI 的 /api/chat、/api/tools/call 等端点，不通过 UI。理由：

  1. 可复现：API 调用是同步、结构化的，可精确控制输入和捕获完整 trace（TraceCollector 已在 API 层工作）。
  2. 可自动判分：DeepEval 的 TaskCompletenessMetric 等指标需要结构化的 LLMTestCase（input / actual_output / expected_output / trace），API 层天然提供这些数据。
  3. 批量效率：22 项测试用例（已有）+ 未来扩展，API 并行运行远快于 UI 串行操作。
  4. 与业界对齐：SWE-bench / AgentBench / DeepEval 全部 API 接入，生态和最佳实践成熟。

UI 层只需验证：Agent 返回的消息能否正确渲染到聊天面板——这属于前端集成测试范畴（vitest + Testing Library），不属于 Agent 评测。

5.4 前端 UI 测试的必要性和范围

前端 UI 测试分层建议

测试类型 必要性 工具 范围
组件逻辑测试 必须 vitest + Testing Library 所有组件（jsdom，不开浏览器）
组件交互流测试 必须 vitest + Testing Library + MSW 关键用户流（发送消息、工具调用展示、错误提示）
视觉回归测试 建议 Playwright 截图对比 核心页面布局（dev 模式 localhost）
Tauri IPC E2E 少量必须 tauri-driver 仅关键路径冒烟（3-5 个用例）
全量 UI E2E 不必要 — 成本高、收益低，用集成测试替代

核心原则：用 vitest + Testing Library 覆盖 90% 的前端测试需求（不开浏览器）；只在"必须验证 Tauri 原生集成"时才用 tauri-driver 做 E2E，且保持在 3-5 个关键路径冒烟用例。

5.5 三条测试线的关系

图 6：三条测试线通过 API 边界松耦合汇合，而非在 UI 层强行打通

三条线的关系：

  • 前端测试线独立验证 UI 渲染和交互，通过 mock API 与后端解耦——前端不依赖真实后端即可测试。
  • 后端测试线独立验证 API 契约和业务逻辑，通过 TestClient 直接调 FastAPI——不依赖前端。
  • Agent 评测线独立验证 AI 决策质量，通过 API 端点接入——不依赖前端也不依赖完整后端基础设施。
  • 三条线在 API 边界（FastAPI 端点契约）松耦合汇合：前端 mock 这个契约、后端实现这个契约、Agent 评测通过这个契约接入。只要 API 契约稳定，三条线可独立演进。
  • E2E 冒烟是唯一跨三条线的测试，但只做 3-5 个关键路径，验证"三条线组装在一起时关键流程能跑通"。

5.6 ISO 25010 质量模型映射

FnixAgent 的测试策略应对照 ISO/IEC 25010 的 8 个质量特性，确保无遗漏：

ISO 25010 特性 定义 对应测试层
功能适宜性 (Functional Suitability) 满足功能需求的程度 单元 + 集成 + Agent 评测
性能效率 (Performance Efficiency) 资源使用下的性能表现 集成（负载测试）+ Agent（响应时延）
兼容性 (Compatibility) 与其他系统交互的能力 集成（API 契约）
易用性 (Usability) 用户使用的难易程度 前端测试 + E2E 冒烟
可靠性 (Reliability) 在指定条件下维持性能的程度 集成（错误处理）+ Agent（回退测试）
安全性 (Security) 防止未授权访问的能力 集成（鉴权测试）+ 静态分析
可维护性 (Maintainability) 可被有效修改的程度 静态分析 + 单元测试覆盖
可移植性 (Portability) 可被迁移的程度 跨平台 E2E（tauri-driver 多平台）

来源：ISO/IEC 25010:2011 软件产品质量模型；综述见 Perforce "What is ISO 25010"

5.7 ISTQB 测试层级映射

ISTQB Foundation Level 大纲定义了四个测试层级，FnixAgent 的四层架构与之对应：

ISTQB 层级 定义 FnixAgent 对应
组件测试 (Component) 单个组件 / 单元的测试 第一层：vitest / pytest / cargo test
集成测试 (Integration) 组件间接口的测试 第二层：前端↔API mock、API↔LangGraph
系统测试 (System) 整个系统的端到端行为 第三层（Agent 系统评测）+ 第四层（E2E 冒烟）
验收测试 (Acceptance) 确认系统满足用户需求 Agent 评测的任务完成度 + 用户级 E2E
