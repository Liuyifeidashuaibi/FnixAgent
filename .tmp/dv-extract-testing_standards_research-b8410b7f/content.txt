[html:l60] 1 ISO/IEC 25010 软件质量模型
[html:l62] ISO/IEC 25010 是 SQuaRE（Systems and software Quality Requirements and Evaluation）系列标准的核心部分，定义了软件产品质量的标准化框架。2011 版定义了 8 个质量特性 和 31 个子特性；2023 版（ISO/IEC 25010:2023）进行了重要修订，新增了 Safety（安全性） 作为独立特性，并以 Interaction Capability（交互能力） 取代了原 Usability（易用性），子特性总数扩展至 31 个。中国国家标准 GB/T 25000.10 等同采用该标准。
[html:l65] ⚠️ 版本说明
[html:l66] 目前业界广泛使用的是 2011 版的 8 特性模型 。2023 版虽然已发布，但大多数测试工具和教材仍基于 2011 版。本报告以 2011 版 8 特性为主线，并在相关位置标注 2023 版变化。

[html:l114] 1.2 各特性详解与测试要点
[html:l116] ① 功能适合性 Functional Suitability
[html:l118] 子特性 定义 测试要点
[html:l119] 功能完整性 Completeness 覆盖所有指定任务和用户目标 需求覆盖度追踪矩阵；验证所有需求项均有对应测试
[html:l120] 功能正确性 Correctness 提供准确结果的能力 正常/异常/边界条件下的输出验证；等价类与边界值分析
[html:l121] 功能适当性 Appropriateness 功能是否适合完成任务 用户场景验证；UX 评审；"做正确的事"而非仅"正确地做事"
[html:l124] ② 性能效率 Performance Efficiency
[html:l126] 子特性 定义 测试要点
[html:l127] 时间特性 Time Behavior 响应时间、处理速度、吞吐量 负载测试、压力测试、并发测试；P99 延迟监控
[html:l128] 资源利用性 Resource Utilization CPU、内存、网络、磁盘 I/O 资源监控工具（如 perfmon、htop）；内存泄漏检测
[html:l129] 容量 Capacity 可处理的数据/用户/事务上限 容量规划测试；渐进加压至系统瓶颈
[html:l132] ③ 兼容性 Compatibility
[html:l134] 子特性 定义 测试要点
[html:l135] 共存性 Co-existence 与其他系统共享环境时的表现 多应用并行运行测试；资源竞争场景
[html:l136] 互操作性 Interoperability 与指定系统交换数据的能力 API 兼容性测试；数据格式验证；协议合规性
[html:l139] ④ 易用性 Usability 2023 版更名为 Interaction Capability
[html:l141] 子特性 定义 测试要点
[html:l142] 可辨识性 Recognizability 用户能否识别系统是否满足需求 UI 清晰度；首次使用引导测试
[html:l143] 可学习性 Learnability 学习使用的难易程度 新用户可用性测试；任务完成时间测量
[html:l144] 可操作性 Operability 操作是否方便 操作步骤数统计；错误恢复便利性
[html:l145] 用户错误防护 User Error Protection 防止用户输入错误 输入验证；确认对话框；撤销功能
[html:l146] 用户界面美观性 UI Aesthetics UI 设计的视觉吸引力 设计评审；A/B 测试
[html:l147] 可访问性 Accessibility 残障人士使用的程度 WCAG 合规检查；屏幕阅读器测试
[html:l150] ⑤ 可靠性 Reliability
[html:l152] 子特性 定义 测试要点
[html:l153] 成熟性 Maturity 降低内部错误引发失效的频率 长时间稳定性测试（soak test）；故障率统计
[html:l154] 可用性 Availability 系统可操作和可访问的程度 MTBF / MTTR 计算；99.9% 等可用性 SLA 验证
[html:l155] 容错性 Fault Tolerance 面对硬件/软件故障仍能运行 故障注入测试（Chaos Engineering）；断网/断电恢复
[html:l156] 可恢复性 Recoverability 恢复受损数据和建立期望状态 灾难恢复测试；数据一致性校验
[html:l159] ⑥ 安全性 Security 2023 版拆分为 Security + Safety
[html:l161] 子特性 定义 测试要点
[html:l162] 保密性 Confidentiality 数据仅被授权者访问 渗透测试；SQL 注入/XSS/CSRF 检测；数据加密验证
[html:l163] 完整性 Integrity 防止未授权修改 数据篡改检测；权限边界测试；审计日志
[html:l164] 不可否认性 Non-repudiation 行为可被证明 数字签名验证；操作日志追溯
[html:l165] 可核查性 Accountability 行为可被唯一追踪到实体 用户行为审计；访问控制列表验证
[html:l166] 真实性 Authenticity 身份验证的能力 认证机制测试；多因素验证；会话管理
[html:l169] ⑦ 可维护性 Maintainability
[html:l171] 子特性 定义 测试要点
[html:l172] 模块化 Modularity 组件可独立修改 架构评审；耦合度分析；模块覆盖率
[html:l173] 可复用性 Reusability 资产可被复用 代码重复度检测；公共库设计评审
[html:l174] 可分析性 Analysability 诊断缺陷和影响的能力 日志完整性；监控告警；可调试性评估
[html:l175] 可修改性 Modifiability 可被修改而不引入缺陷 回归测试通过率；变更影响分析
[html:l176] 可测试性 Testability 可被有效测试 测试覆盖率；测试自动化程度；依赖注入
[html:l179] ⑧ 可移植性 Portability
[html:l181] 子特性 定义 测试要点
[html:l182] 适应性 Adaptability 适应不同环境 跨平台测试（Windows/macOS/Linux）；分辨率适配
[html:l183] 可安装性 Installability 指定环境中安装的难易 安装/卸载测试；升级测试；权限要求验证
[html:l184] 可替换性 Replaceability 替代另一指定软件的能力 版本兼容性；数据迁移测试
[html:l187] 1.3 基于 ISO 25010 设计测试用例的方法
[html:l190] 📐 质量驱动的测试设计框架
[html:l191] ISO 25010 的核心价值在于提供了一套 结构化的质量需求分解方法 ，将"软件质量"这个模糊概念拆解为可测试的具体维度。
[html:l194] 设计步骤：
[html:l196] 需求映射 ：将产品需求逐一映射到 8 个质量特性，标注每个需求涉及哪些子特性
[html:l197] 优先级排序 ：根据业务风险对质量特性排序（如金融系统：安全性 > 可靠性 > 性能；游戏：性能 > 易用性）
[html:l198] 指标量化 ：为每个子特性定义可测量的验收标准（如"P99 响应时间
[html:l199] 技术选择 ：根据质量特性选择对应的测试技术（功能→黑盒技术；性能→负载测试；安全→渗透测试）
[html:l200] 用例编写 ：以"质量特性 + 子特性 + 场景 + 预期结果"格式编写测试用例
[html:l203] 以"用户登录功能"为例的 8 特性覆盖：
[html:l205] 质量特性 测试用例示例
[html:l206] 功能适合性 正确账号密码可登录；错误密码提示报错；验证码功能正常
[html:l207] 性能效率 登录响应 < 1s；1000 并发登录无超时
[html:l208] 兼容性 Chrome/Safari/Firefox 均可登录；不同操作系统下正常
[html:l209] 易用性 新用户 30s 内完成首次登录；密码错误有明确提示
[html:l210] 可靠性 连续 72h 运行无故障；断网后重连可恢复登录状态
[html:l211] 安全性 密码加密存储；无 SQL 注入；会话超时自动登出
[html:l212] 可维护性 登录模块修改后回归测试通过率 100%
[html:l213] 可移植性 从 Windows 迁移到 macOS 后登录功能正常
[html:l220] 2 ISTQB 测试体系
[html:l222] ISTQB （International Software Testing Qualifications Board）是全球最大的软件测试认证体系，已在 130+ 个国家发放超过 110 万张证书。其基础级大纲 CTFL v4.0 （2023 年 4 月发布，2024 年 11 月全面替代 v3.1）是软件测试领域的通用知识体系，被业界视为测试术语和方法的"事实标准"。
[html:l225] 📖 ISTQB 七大测试原则
[html:l226] ① 测试显示缺陷存在，而非缺席 — 测试能发现缺陷，但不能证明没有缺陷
[html:l227] ② 穷尽测试不可能 — 除简单情况外无法测试所有组合，应基于风险和优先级
[html:l228] ③ 尽早测试 — 越早发现缺陷修复成本越低（Shift-Left）
[html:l229] ④ 缺陷集群效应 — 少数模块通常包含大部分缺陷（二八定律）
[html:l230] ⑤ 农药悖论 — 重复执行相同测试不再发现新缺陷，需定期更新测试用例
[html:l231] ⑥ 测试活动依赖于测试上下文 — 不同场景需要不同测试方法
[html:l232] ⑦ "无缺陷"谬误 — 没有发现缺陷 ≠ 系统满足用户需求
[html:l235] 2.1 测试级别 Test Levels
[html:l237] ISTQB 定义了 4 个测试级别，从微观到宏观逐层递进：
[html:l240] 测试级别 测试对象 目标 典型工具 执行者
[html:l242] 组件测试 Component Testing (单元测试)
[html:l243] 单个模块/函数/类
[html:l244] 验证组件内部逻辑正确性；尽早发现编码缺陷
[html:l245] pytest, JUnit, Jest, cargo test
[html:l246] 开发人员
[html:l249] 组件集成测试 Component Integration
[html:l250] 组件间接口与交互
[html:l251] 验证组件组装后的接口调用、数据流、控制流正确性
[html:l252] pytest, Postman, Supertest
[html:l253] 开发人员 / 测试人员
[html:l256] 系统测试 System Testing
[html:l257] 整个系统
[html:l258] 验证系统端到端功能和非功能特性是否满足需求规格
[html:l259] Selenium, Playwright, JMeter
[html:l260] 独立测试团队
[html:l263] 验收测试 Acceptance Testing
[html:l264] 系统在真实环境中
[html:l265] 确认系统满足用户需求；决定是否接受系统
[html:l266] 手动验收, UAT 工具
[html:l267] 用户 / 客户 / 产品
[html:l272] 📋 验收测试的四种形式
[html:l273] 用户验收测试 (UAT) ：最终用户在真实环境中验证系统是否满足业务需求
[html:l274] 运行验收测试 (OAT) ：验证系统在生产环境中的可运维性（部署、监控、备份恢复）
[html:l275] 合同验收测试 ：依据合同条款验证是否满足验收标准
[html:l276] Alpha/Beta 测试 ：Alpha 在开发方环境由内部用户测试；Beta 在客户环境由真实用户测试
[html:l279] 2.2 测试类型 Test Types
[html:l282] 测试类型 关注点 对应 ISO 25010 特性 示例
[html:l284] 功能测试
[html:l285] 系统"做什么" — 功能完整性、正确性、适当性
[html:l286] 功能适合性
[html:l287] 验证登录功能、文件上传、API 响应
[html:l290] 非功能测试
[html:l291] 系统"做得好不好" — 性能、安全、易用性等
[html:l292] 其余 7 个特性
[html:l293] 负载测试、渗透测试、兼容性测试
[html:l296] 白盒测试
[html:l297] 基于内部结构 — 代码、控制流、数据流
[html:l298] —
[html:l299] 语句覆盖、分支覆盖、路径覆盖
[html:l302] 黑盒测试
[html:l303] 基于规格说明 — 不关心内部实现
[html:l304] —
[html:l305] 等价类划分、边界值分析
[html:l309] ISTQB 强调： 四种测试类型可应用于所有测试级别 。例如，单元测试也可以做性能测试（如函数执行时间），系统测试也可以做白盒测试（如代码覆盖率分析）。
[html:l311] 此外，ISTQB 还定义了两类特殊测试：
[html:l313] 确认测试 (Confirmation Testing) ：缺陷修复后，重新执行原来失败的测试以验证修复有效
[html:l314] 回归测试 (Regression Testing) ：修改后重新执行未变更部分的测试，确保未引入新缺陷
[html:l317] 2.3 测试设计技术 Test Design Techniques
[html:l319] ISTQB 将测试设计技术分为三大类： 黑盒 、 白盒 和 基于经验 。
[html:l321] 黑盒测试技术
[html:l324] 技术 核心思想 适用场景 示例
[html:l326] 等价类划分 Equivalence Partitioning
[html:l327] 将输入域划分为等价类，每类取一个代表值
[html:l328] 输入范围明确的场景
[html:l329] 密码长度 8-32：取 7(无效)、8(有效)、32(有效)、33(无效)
[html:l332] 边界值分析 Boundary Value Analysis
[html:l333] 缺陷往往出现在边界，重点测试边界值及其邻域
[html:l334] 数值范围、数组边界
[html:l335] 范围 [0, 100]：测试 -1, 0, 1, 99, 100, 101
[html:l338] 决策表测试 Decision Table Testing
[html:l339] 列出所有条件组合及其对应动作
[html:l340] 多条件组合的复杂业务逻辑
[html:l341] 登录逻辑：账号正确×密码正确×验证码正确 → 8 种组合
[html:l344] 状态迁移测试 State Transition Testing
[html:l345] 识别系统状态和触发迁移的事件，测试所有迁移路径
[html:l346] 有状态的系统（订单、审批流）
[html:l347] 订单：待支付→已支付→已发货→已完成 / 已取消
[html:l350] 用例测试 Use Case Testing
[html:l351] 基于用户场景设计端到端测试
[html:l352] 系统级验收测试
[html:l353] 用户从浏览商品到完成下单的完整流程
[html:l357] 白盒测试技术
[html:l360] 技术 覆盖标准 说明
[html:l361] 语句覆盖 Statement Coverage 每条语句至少执行一次 最弱的覆盖标准，不保证分支正确
[html:l362] 分支/判定覆盖 Branch Coverage 每个分支的真/假路径至少执行一次 比语句覆盖更强，业界常用最低标准
[html:l363] 分支/条件覆盖 Branch/Condition 每个条件的真/假均至少执行一次 处理复合条件 (a && b) 的子条件
[html:l364] 路径覆盖 Path Coverage 所有独立执行路径至少执行一次 最强但成本最高，循环场景下路径数爆炸
[html:l365] MC/DC 修正条件/判定覆盖 每个条件独立影响判定结果 航空安全软件 (DO-178C) 强制要求
[html:l368] 基于经验的测试技术
[html:l371] 技术 说明 适用场景
[html:l372] 错误猜测 Error Guessing 基于经验预判可能出错的点 有经验的测试人员补充测试用例
[html:l373] 探索式测试 Exploratory Testing 边设计边执行，强调学习和适应 敏捷开发中快速发现未知缺陷
[html:l374] 检查表测试 Checklist-based 基于经验积累的检查清单逐项验证 回归测试、安全检查

[html:l379] • 新增 DevOps 和 CI/CD 中的测试 章节
[html:l380] • 引入 测试金字塔 和 测试象限 (Testing Quadrants) 概念

[html:l389] 3 测试金字塔与测试策略
[html:l391] 3.1 测试金字塔模型
[html:l393] 测试金字塔 (Test Automation Pyramid) 由 Mike Cohn 在 2009 年《Succeeding with Agile》中提出，是指导自动化测试分层策略的经典模型。核心思想： 大量快速的底层测试 + 少量慢速的顶层测试 。
[html:l397] E2E 测试 ~5-10%
[html:l400] 集成测试 ~15-20%
[html:l403] 单元测试 ~70-80%
[html:l408] 层级 占比 特点 执行速度 维护成本 信心
[html:l409] 单元测试 70-80% 验证单个函数/模块逻辑；隔离外部依赖 毫秒级 低 中
[html:l410] 集成测试 15-20% 验证模块间接口和数据流；mock 外部服务 秒级 中 高
[html:l411] E2E 测试 5-10% 模拟真实用户操作完整流程 分钟级 高 最高
[html:l414] 3.2 哪些层该自动化
[html:l418] ✅ 必须自动化
[html:l420] 单元测试 ：100% 自动化，每次提交都跑
[html:l421] 集成测试 ：API 契约、数据流验证自动执行
[html:l422] 回归测试 ：核心路径的回归用例库
[html:l423] 构建/部署流水线 ：CI/CD 中的自动化质量门禁
[html:l427] ⚠️ 谨慎自动化
[html:l429] E2E 测试 ：仅覆盖 3-5 条核心用户路径，避免维护噩梦
[html:l430] 视觉/UI 测试 ：使用视觉回归工具而非逐像素比较
[html:l431] 探索式测试 ：本质上需要人类智慧，自动化仅作辅助
[html:l436] 3.3 替代与补充模型
[html:l438] Testing Trophy（Kent C. Dodds, 2019）
[html:l439] 前端测试专家 Kent C. Dodds 提出 测试奖杯 模型，认为 集成测试的投入产出比最高 ，应占据最大比例。核心理念： "Write tests. Not too many. Mostly integration."
[html:l441] 底层：静态分析（TypeScript/ESLint）— 成本极低
[html:l442] 中层： 集成测试（占大头） — 最高 ROI
[html:l443] 顶层：少量 E2E + 单元测试
[html:l446] 常见反模式
[html:l449] 🚫 反模式：冰淇淋蛋筒 (Ice Cream Cone)
[html:l450] 顶层 E2E 最多，底层单元最少 。导致：测试套件运行极慢、任何 UI 变动都引发大量失败、维护成本远超收益。这是最常见的测试反模式。
[html:l454] 🚫 反模式：纸杯蛋糕 (Cupcake)
[html:l455] 手工测试占比过大 ，自动化测试不足。每个版本都需要大量手工回归，无法支持持续交付。

[html:l546] 4.4 缺陷管理 Defect Management
[html:l548] 缺陷生命周期遵循标准状态流转：
[html:l550] 新建 (New)

[html:l575] 策略 说明 适用场景
[html:l576] 全量回归 执行所有已有测试用例 大版本发布前
[html:l577] 选择性回归 基于变更影响分析，仅执行受影响模块的测试 日常迭代
[html:l578] 基于风险的回归 优先执行高风险模块和核心路径的测试 紧急修复发布

[html:l758] AI Agent 类应用（如 FnixAgent）的测试是软件测试领域的前沿课题。传统软件测试的"输入→输出"确定性验证范式在 AI 系统中面临根本性挑战： 相同输入可能产生不同输出，输出正确性难以精确定义 。
[html:l760] 6.1 LLM 评测 vs Agent 评测：本质差异
[html:l763] 维度 传统 LLM 评测 Agent 评测
[html:l764] 交互模式 单步问答（1 次输入 → 1 次输出） 多步序列决策（5-50 步长链任务）
[html:l765] 环境交互 封闭式，无外部环境 开放式，与浏览器/终端/API/文件系统交互
[html:l766] 评估对象 最终答案质量 过程轨迹 + 最终结果 + 中间行为合规性
[html:l767] 正确性标准 答案匹配（Exact Match / BLEU / ROUGE） 任务是否完成（成功率）+ 过程质量
[html:l768] 成本考量 忽略 核心指标（Token 消耗、API 调用次数、执行时间）
[html:l769] 工具调用 不支持 核心能力（选对工具 + 参数正确 + 时机合适）
[html:l770] 错误恢复 不适用 关键指标（检测错误 → 修正 → 继续执行）
[html:l771] 可靠性要求 单次准确率 端到端成功率（多步中任一步出错则失败）
[html:l775] ⚠️ 关键洞察
[html:l776] 一个在 HumanEval（代码生成基准）上 95 分的模型，放到 SWE-bench（真实仓库修 Bug）上可能只有 30% 的通过率。原因： Agent 的端到端成功率是各步成功率的乘积 ，10 步任务中每步 90% 成功率，整体成功率仅 35%。

[html:l911] 6.5 分层阶梯式评测方法（Google/DeepMind 实践）
[html:l913] Google DeepMind 团队采用按难度分层的评测策略，评测成本与风险匹配：
[html:l916] 层级 评测对象 评测方法 自动化程度
[html:l917] Level 1 基础能力（单轮问答、翻译、摘要） 自动化指标（Exact Match / BLEU） 全自动化
[html:l918] Level 2 推理能力（多步推理、代码生成） LLM-as-Judge + 部分自动化 半自动化
[html:l919] Level 3 Agent 能力（工具使用、规划、自主执行） 端到端任务 + Trace 分析 半自动化
[html:l920] Level 4 安全与对齐（红队测试、偏见检测） 专项评测 + 人工审核 低自动化
[html:l923] 6.6 LLM-as-a-Judge 范式
[html:l925] 对于没有唯一正确答案的 Agent 任务（如"帮我规划一个项目方案"），传统精确匹配失效。 LLM-as-a-Judge 使用一个更强的模型作为裁判，根据评分规则（Rubric）对 Agent 的执行轨迹和输出进行评分：
[html:l928] 评分维度 ：工具使用合理性、计划可行性、回答完整性、安全性
[html:l929] 评分方式 ：Chain-of-Thought 推理 → 结构化评分（1-5 分）+ 评分理由
[html:l930] 注意事项 ：Judge 模型应强于被测模型；需校准 Judge 的一致性；多 Judge 投票可提升可靠性

[html:l949] 6.8 FnixAgent Agent 评测体系现状与建议
[html:l952] ✅ 已有基础
[html:l953] FnixAgent 已自研 Agent 评测工具（ tests/agent_eval/ ），包含 4 个模块：
[html:l955] TraceCollector ：采集 Agent 执行轨迹（思考链、工具调用、中间状态）
[html:l956] ProblemDetector ：基于轨迹检测问题模式（重复调用、死循环、工具错误等）
[html:l957] EvalRunner ：批量执行评测用例，收集结果
[html:l958] ReportGenerator ：生成可视化评测报告
[html:l960] 已有 22 项测试用例覆盖 8 类场景，通过率 86.4%。
[html:l964] 💡 进阶建议
[html:l965] 1. 引入 DeepEval 补充自动化指标 ：将 DeepEval 的 Task Completion、Tool Correctness 等指标集成到现有 EvalRunner 中，获得更结构化的评分。
[html:l966] 2. 建立 LLM-as-Judge 评分层 ：对于开放性任务（如代码生成质量、方案合理性），使用更强的模型（如 Claude Opus）作为 Judge，按 Rubric 评分。
[html:l967] 3. 扩展评测集 ：从 22 个 case 扩展到 200+，覆盖正常流程 60% + 边缘 case 20% + 异常场景 20%。
[html:l968] 4. 添加鲁棒性测试 ：注入随机干扰（工具超时、API 异常、网络中断），测试 Agent 的错误恢复能力。
[html:l969] 5. 建立成本追踪 ：在 TraceCollector 中记录每任务的 Token 消耗和 API 调用次数，纳入评测报告。
[html:l970] 6. 参照 GAIA 构建内部基准 ：从真实用户使用场景中提取任务，构建 FnixAgent 专属的"GAIA 基准"。
