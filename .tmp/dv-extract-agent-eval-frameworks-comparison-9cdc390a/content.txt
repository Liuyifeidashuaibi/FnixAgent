[html:l71] 核心能力：如何检测 Agent 每一步问题
[html:l72] DeepEval 通过 轨迹评估（Trajectory Evaluation） 机制检测 Agent 执行过程中的每一步。核心思路是：用 @observe() 装饰器或 trace() 上下文管理器自动捕获 Agent 的完整执行轨迹，包括每一步的输入、输出、工具调用、参数等，然后将轨迹传给 Agentic Metrics 进行评分。

[html:l79] def inner_component(input: str):
[html:l80] output = "result"
[html:l81] update_current_span(test_case=LLMTestCase(input=input, actual_output=output))
[html:l82] return output
[html:l84] @observe()
[html:l85] def app(input: str):
[html:l86] return inner_component(input)

[html:l92] 内置 Agentic 指标详解
[html:l93] DeepEval 提供 8 个 Agent 专用指标，分两个层次运行： 端到端层 （看最终结果）和 轨迹层 （看执行过程）。
[html:l96] 指标 检测什么 计算方式 层次
[html:l98] TaskCompletionMetric
[html:l99] Agent 是否达成了用户目标
[html:l100] LLM-as-judge：将 Agent 最终输出与预期目标对比，判断任务是否完成。输出 0-1 分数 + 评分理由
[html:l101] 端到端
[html:l104] ToolCorrectnessMetric
[html:l105] 是否调用了正确的工具、参数是否正确
[html:l106] 确定性规则优先 ：先按工具名匹配，再比较参数。支持 strict / unordered / subset 等匹配模式。不确定部分才用 LLM judge
[html:l107] 轨迹
[html:l110] GoalAccuracyMetric
[html:l111] Agent 达成目标的精确程度
[html:l112] LLM-as-judge：评估最终输出与理想答案的语义相似度和准确性
[html:l113] 端到端
[html:l116] StepEfficiencyMetric
[html:l117] Agent 是否走了不必要的弯路
[html:l118] 比较实际步数与最优步数。如 3 步能完成的任务用了 9 步（含重试），效率分 = 最优步数/实际步数
[html:l119] 轨迹
[html:l122] PlanAdherenceMetric
[html:l123] Agent 是否遵循了预期计划
[html:l124] 将实际执行轨迹与预期计划对比，检测是否中途跑偏。支持无显式计划的场景
[html:l125] 轨迹
[html:l128] PlanQualityMetric
[html:l129] Agent 的规划质量
[html:l130] LLM-as-judge：评估 Agent 制定的计划是否合理、是否覆盖了所有必要步骤、顺序是否正确
[html:l131] 轨迹
[html:l134] ToolUseMetric
[html:l135] 工具使用的整体质量
[html:l136] 综合评估工具选择是否恰当、调用时机是否合理、结果处理是否正确
[html:l137] 轨迹
[html:l140] ArgumentCorrectnessMetric
[html:l141] 工具调用参数的合法性
[html:l142] 确定性校验：参数类型、必填项、值域是否符合 Schema 定义。可结合 Schema 验证
[html:l143] 轨迹
[html:l148] 指标计算原理 ：所有指标输出 0.0 ~ 1.0 的分数及 score_reason （评分理由）。默认阈值 threshold=0.5 ，低于阈值则测试失败。轨迹层指标需要提供 tools_called 和 expected_tools 信息；端到端指标只需 actual_output 和 expected_output 。
[html:l151] LLM-as-judge 机制与配置
[html:l152] DeepEval 的 LLM-as-judge 支持三种评估技术：
[html:l154] G-Eval ：基于思维链（CoT）的评分，用自然语言描述评分标准，LLM 逐步推理后给出分数。适合主观维度
[html:l155] DAG（Directed Acyclic Graph） ：决策图评分，定义多步条件判断流程。适合客观、多步骤的评分
[html:l156] QAG（Question-Answer Generation） ：生成封闭式问题并用参考答案验证。适合有明确答案的场景

[html:l539] 5. Agent-Eval-Harness 分析
[html:l542] 重要说明 ：经过多轮搜索（GitHub、技术博客、学术数据库），未找到一个名为 "Agent-Eval-Harness" 的独立开源项目。该名称可能指的是一类"语言无关的评测 harness"设计范式，而非特定项目。以下分析基于该范式最接近的实际实现： hal-harness （Princeton PLI）和 Harbor （Terminal-Bench 环境），它们体现了用户描述的核心特征。
[html:l545] 最接近的实际项目
[html:l547] 1. hal-harness（Princeton PLI）
[html:l549] 项目 详情
[html:l550] GitHub princeton-pli/hal-harness
[html:l551] 内置基准 GAIA、Terminal-Bench、SWE-bench Verified、CORE-bench、tau-bench、SciCode、AssistantBench、Cybench 等
[html:l552] Agent 接入 支持 Inspect Solver agents（ @solver 装饰器）和 自定义外部 Agent
[html:l553] 执行环境 本地或 Azure VM（ --vm 标志），支持完全并行化评测
[html:l555] hal-harness 的核心设计是：将 Agent 视为外部进程，通过 CLI 接口驱动。自定义 Agent 只需实现约定的输入/输出协议即可接入，理论上语言无关。
[html:l557] 2. Harbor（Terminal-Bench 环境）
[html:l559] 项目 详情
[html:l560] GitHub ucsb-mlsec/terminal-bench-env
[html:l561] 安装 pip install harbor
[html:l562] 支持的基准 Terminal-Bench 2.0、SWE-bench Verified

[html:l565] # 在 Terminal-Bench 2.0 上运行自定义 Agent
[html:l566] harbor run -d terminal-bench@2.0 \
[html:l567] --agent-import-path my_agent:MyAgent \

[html:l575] 语言无关接入方式的实现思路
[html:l576] "语言无关"的核心思路是：Agent 和 Harness 之间通过 标准化的 JSON 协议 （stdin/stdout）通信，而非直接调用 Python API：
[html:l577] # Harness 发送任务（JSON via stdin）
[html:l578] {
[html:l579] "task_id": "gaia_001",
[html:l580] "instruction": "Find the population of Tokyo in 2024",
[html:l581] "tools": ["web_search", "bash"],
[html:l582] "max_steps": 20
[html:l583] }
[html:l585] # Agent 返回结果（JSON via stdout）
[html:l586] {
[html:l587] "answer": "Tokyo's population in 2024 is approximately 14 million",
[html:l588] "steps": [...],
[html:l589] "tool_calls": [...]
[html:l590] }
[html:l591] 这种设计的优势是：Agent 可以用任何语言实现（Rust、Node.js、Go），只要遵循 JSON 协议即可被 Harness 驱动。
[html:l593] 适合 Rust/Node Agent 的原因
[html:l595] 进程隔离 ：Agent 作为独立进程运行，Harness 不关心 Agent 的实现语言
[html:l596] 无 Python 依赖 ：不需要在 Agent 进程中安装 Python 库
[html:l597] Docker 沙箱 ：每个任务在独立 Docker 容器中执行，环境隔离
[html:l598] 并行执行 ： --n-concurrent 控制并行度，适合大规模评测
[html:l602] 对 FnixAgent 的适用性 ：FnixAgent 后端是 Python/FastAPI，直接用 Python SDK 类框架（DeepEval/EvalScope）更自然。语言无关的 harness 方案更适合 Rust/Node/Go 实现的 Agent，对 FnixAgent 来说接入成本偏高。

[html:l717] 7. 关键问题解答
[html:l719] 问题 1：哪个框架最适合接入 FnixAgent？
[html:l722] 推荐：DeepEval（首选）+ EvalScope（补充）
[html:l725] FnixAgent 的技术栈是 Python/FastAPI 后端 + HTTP API 调用 + 百炼 kimi-k2.5，已有的自研评测工具（TraceCollector + ProblemDetector + EvalRunner）覆盖 22 个测试用例、8 类场景。基于这些条件分析：
[html:l728] 考量因素 DeepEval 为什么不选其他
[html:l730] Python 原生
[html:l731] FnixAgent 后端是 Python，直接 import 使用，零适配成本
[html:l732] Agent-Eval-Harness 需实现 JSON 协议层，过度设计
[html:l735] HTTP API 接入
[html:l736] 用 requests.post() 调用 FnixAgent API，构造 LLMTestCase 即可
[html:l737] AgentBench 需实现适配器接口 + 配置 Docker 环境
[html:l740] 问题检测覆盖
[html:l741] 8 个 Agentic 指标精确映射 5 类问题（见下方对比）
[html:l742] LangSmith 无内置 Agentic 指标，需自定义评估器
[html:l745] CI/CD 集成
[html:l746] pytest 原生， deepeval test run 直接嵌入 GitHub Actions
[html:l747] EvalScope 偏批量评测，CI 集成需额外封装
[html:l750] 与现有工具互补
[html:l751] FnixAgent 已有 ProblemDetector，DeepEval 可作为补充验证层
[html:l752] LangSmith 是 Trace 平台，与 ProblemDetector 功能重叠
[html:l755] 成本
[html:l756] 开源免费，Confident AI 云平台也免费
[html:l757] LangSmith 免费版仅 5k Trace/月、100 次评估/月
[html:l761] 补充方案：EvalScope 。当需要进行模型选型横向对比（如 kimi-k2.5 vs Qwen vs DeepSeek）或跑 SWE-bench/GAIA 基准时，EvalScope 的 Arena 模式和内置基准是最佳补充。两者可并行使用：DeepEval 做 CI/CD 回归测试，EvalScope 做阶段性基准评测。
